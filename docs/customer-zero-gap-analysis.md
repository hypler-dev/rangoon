## Required architecture changes

### 1. Add a durable service mode over reusable application contracts

Rangoon's desktop is currently the native application host. A task that must survive Codex closing needs an independently supervised Rangoon service or qualified external runtime, not an MCP request or desktop window holding its only state. Extend the modular architecture with reusable application use cases and thin UI/CLI/MCP adapters; retain one logical task authority. A service process restart may require reconciliation: durability is not a promise that every task continues uninterrupted.

Start with one controller and one isolated worker. Keep a separately versioned operational store and bounded artifact references; do not put unbounded logs/jobs into the content workspace's existing 64 MiB limit or network-share its SQLite file. The operational store's encryption, service-owned key custody, migrations, quotas, retention, backup and recovery need explicit tests. A headless process cannot silently inherit a desktop unlock or vault permission. Multi-controller shared metadata and high availability remain later measured needs; the first pilot does not require PostgreSQL, a new cluster or a hypervisor.

### 2. Separate a task from its attempts, runtime jobs and effects

Define versioned task identity and pinned input/scope/resource requirements, then distinct attempt identities, runtime-native job references, ownership/fences, deadlines, progress, artifacts and reconciliation. Reuse existing authored workflow/capability revisions as inputs and existing evidence concepts as projections; do not mutate either into a job queue.

Submission must be idempotent for an identical caller-scoped key and payload; conflicting reuse is refused. Distinguish queued, assigned, starting, running, awaiting approval, cancellation requested, completed, failed, outcome unknown and reconciliation required. Define exact legal transitions before implementation. A cancelled request is not proof that a process stopped; lease expiry is not proof that an earlier attempt cannot still have effects. Do not promise distributed exactly-once execution. Unknown consequential outcomes cannot be retried or moved to another worker automatically.

### 3. Integrate one execution runtime before building scheduling infrastructure

Rangoon can own task priority, eligible worker/resource/privacy constraints and placement preference. One selected runtime owns physical dispatch, native process lifecycle and its own allocation/lease mechanics. Preserve that ownership through an adapter; do not create two competing schedulers or treat a native job identifier as authenticated evidence without qualification.

Evaluate Dagu against the exact pilot and a minimal OS-supervised runner. Dagu already documents [server queues/coordinator and distributed workers](https://docs.dagu.sh/overview/deployment-models) and a built-in [MCP surface](https://docs.dagu.sh/mcp/). Its generic run/edit tools must not become Rangoon's unrestricted agent API. Check cancellation, crash recovery, worker identity, isolation, result durability, API versioning, resource use and data handling. Do not assume a scheduler is a sandbox. Its [GPL-3.0-or-later and embedding terms](https://docs.dagu.sh/embedding/licensing) require distribution review; do not embed its Go API into an Apache-2.0 deliverable by default. Product selection and license suitability remain open, not legal conclusions or installation authority.

Proxmox, OpenHands, LiteLLM and observability products remain optional candidates when a measured requirement justifies them. Avoid adopting an entire stack to run the first task.

### 4. Implement two distinct agent integration directions

**Agent to Rangoon:** a restricted MCP adapter calls the same durable application service as UI/CLI. Proposed operations are worker inspection, submission of an allowlisted task type, bounded status/results/artifact retrieval and cancellation/approval requests. Submission returns a task reference; a long MCP connection does not own execution. Caller identity, target/project scope, quotas, output limits and idempotency are required. No arbitrary command, path, credential, plugin install or self-expanded permission field belongs in the initial task API.

Pin the actual MCP protocol/SDK/transport and advertised capabilities before implementation. Record the authenticated requester separately from a claimed agent name, worker identity and runtime/model identity; an approval request is not an approval or execution grant. Native task records introduce a new operational concern, not a way to authenticate imported O1/O2 observations. Reuse their provenance concepts only through a separately reviewed mapping.

**Rangoon to an agent:** a provider-specific runner starts and supervises an explicitly selected coding-agent mode in an isolated workspace. Prefer a batch interface for the first bounded job; interactive sessions are later. Official [Codex CLI automation](https://learn.chatgpt.com/docs/developer-commands#codex-exec) documents JSONL batch output. The [Codex App Server](https://learn.chatgpt.com/docs/app-server) offers richer JSON-RPC session/event integration but is experimental and not supported for production workloads. The old [Codex MCP-server command was removed](https://learn.chatgpt.com/docs/mcp-server); Codex can still consume an external Rangoon MCP server. Do not confuse these directions.

Claude documents [programmatic CLI/SDK operation](https://code.claude.com/docs/en/headless), with provider-specific events, controls and errors. Pin and test each runner separately. [Anthropic's credential rules](https://code.claude.com/docs/en/legal-and-compliance#authentication-and-credential-use) distinguish end-user sign-in to its unmodified binary from a third-party product routing subscription credentials. Keep provider sign-in under the user's supported authentication flow; never copy session tokens between workers or promise unlimited subscription concurrency. Service-mediated API funding and user-operated subscription sessions require separate applicability checks. No paid run is needed to qualify task durability.

### 5. Treat source review as code execution inside an isolation boundary

An IZIOS engineering review is read-only with respect to production, but tests, build hooks and validators execute repository-controlled code. Pin a revision and file manifest, transfer an explicitly approved source snapshot without home directories, production credentials or incidental configuration, and create a disposable workspace. At admission, record an immutable validator-profile revision and digest, exact argv without shell evaluation, executable/toolchain identities, sandbox-policy revision, dependency lockfile and isolated cache-snapshot identities, and CPU/memory/disk/time/output limits. The worker verifies the same identities before starting; a changed or unavailable identity refuses execution rather than silently selecting the latest profile, binary, cache or policy. Dependencies/caches are read-only or materialized into an attempt-isolated copy; shared mutable caches cannot redefine an admitted execution. Failed prerequisites are reported as skipped/unavailable, never passed.

Make isolation a fail-closed dispatch invariant, not a best-effort setting. Execute repository code under a dedicated unprivileged identity or qualified equivalent sandbox, separate from the service/worker supervisor. Do not inherit supervisor credentials, host home directories, incidental environment variables, file descriptors, credential stores, host/control-plane sockets, container-runtime sockets, cloud metadata access or unapproved mounts. Supply only the profile's explicit non-secret environment and scoped input/output handles. The supervisor's enrollment identity and control channel remain outside the task process. Default-deny task network access; any necessary exception names the exact destination, purpose, protocol and scope in the admitted profile and requires explicit approval. Missing platform enforcement or an unverifiable exception blocks dispatch. An ordinary process running as the operator, or a scheduler without those controls, does not satisfy this contract.

Bound snapshot/archive size and file counts; refuse traversal, unsafe links, unexpected submodules or substituted inputs. Artifact retrieval uses scoped immutable references, never a caller-supplied host path. A process exit or scanner report is captured evidence, not proof that a production system was safe or unchanged.

Source copies, caches, artifacts, subprocess logs and an external scheduler's files are separate confidentiality surfaces from the encrypted content database. Specify permitted storage volumes, encryption, retention and cleanup. Enforce task isolation before running code; imported instructions and model results cannot alter it. CZ-2 must run negative probes from inside the actual task process: attempts to read synthetic supervisor secrets, host files and inherited handles, reach control/container sockets or cloud metadata, escape source/output mounts, and exfiltrate synthetic source/artifacts through unapproved egress must be denied. Verify resource caps and termination of descendants, not just the initial process. Use canaries and disposable targets; never test against real secrets or production systems. Record actual observed denials and bounded retained evidence per OS/runtime; a configuration file alone is not proof. Redact and bound result text, treat it as untrusted UI input, and preserve original evidence references without publishing secrets. Production applications and database/payment/purchase/deployment operations remain outside this pilot.

### 6. Add accounting before claiming autonomous cost control

Create model/provider capability metadata and a task/attempt usage ledger that distinguishes provider-reported counts, gateway measurements, estimates, reservations and finalized charges. Use explicit units/currency/rate revisions; subscription quota is not API per-token billing. Local resource measurements and energy estimates have different evidence. Unknown usage stays unknown. Dispatch admission, concurrent reservations, retries, cancellation and late settlement require tests before claiming a hard spending cap. Provider-side checkpoints may limit overshoot only where actually supported.

First run deterministic tests and scanners with no model call. Add one authorized model review afterward, then a second provider. Do not use paid inference to exercise scheduler concurrency or train a model to replace deterministic permission checks.

### 7. Present an operational workflow in the existing shell

Use Tasks as the primary Operations entry, with Workers and Usage as related views and a right inspector for the selected task. Keep Import/Skills/Workflows/Compile accessible. Show scope, source revision, attempt, worker/runtime, current phase, last observation, resource limits, cost basis and artifacts. Label unknown, stale, cancellation requested and unverified evidence explicitly. Topology is an alternate view of the same bounded records. Simple/Advanced changes detail, not permissions. Hostnames, inventories and Hypler-specific policies belong in private profiles, not public defaults.

## Revised first acceptance workflow

The proposed first value milestone is the supplied IZIOS source-review job, generalized as a project review task. CZ-2 first qualifies its durable service/runtime path through a CLI, without MCP or a model. CZ-3 then replays that qualified job through Codex and Rangoon MCP, completing the supplied Customer Zero demonstration. These are intermediate and full acceptance gates, not competing definitions of completion. OpenShell finite-read mounting may proceed in its own accepted lane when useful, but is not a prerequisite for deterministic engineering-task execution. Neither LNSAT nor VUSL completion should block an otherwise qualified constrained pilot; unavailable mandatory controls still block affected actions.

1. A user selects a pinned, authorized source snapshot and immutable validator/execution profile. The CLI submits the bounded task for CZ-2; Codex submits it through Rangoon MCP for CZ-3. Both use the same application contract and durable task identity scheme.
2. Rangoon durably records scope, idempotency key, budget/resource admission and input identities before acknowledging submission. The selected runtime receives a distinct attempt with an exact eligible worker binding.
3. The worker revalidates the admitted source and execution identities, establishes the required isolation, then runs only the approved validators and captures bounded structured results/artifact digests. Identity drift or failed isolation refuses the attempt before repository code starts. Model review is optional, separately consented and separately accounted in a later slice.
4. The initiating CLI client disconnects in CZ-2, and Codex disconnects in CZ-3. Another authorized client retrieves the same task, attempt and results. A controller/worker restart test reconciles native state rather than fabricating completion or resubmitting blindly.
5. The operator receives findings, test outcomes, measured resource/usage data, skipped checks, evidence references and remaining unknowns. Native completion, provider claims, local review and verified external effects remain distinct facts.

Before accepting CZ-2, test duplicate/conflicting submissions; wrong scope/worker/revision; mutation of the admitted validator profile, argv, executable/toolchain, sandbox policy or dependency/cache snapshot between submission, dispatch and launch; disabled or missing runtime; denied required authority; worker/controller death; network partition; expired lease and late completion; cancellation before and during execution; disk/output exhaustion; hostile result text; missing/partial artifacts; and uncertain outcomes without automatic rerun. Prove the isolation denials above while the task code runs. Closing the initiating CLI must not lose the task. CZ-3 must repeat the complete submission/disconnect/retrieval path through MCP, including its identity, scope, malformed-request and result-boundary checks, before the full demonstration is complete. Production access and ambient secrets must remain absent. Every test names its actual OS/runtime and observed consequence; source fixtures do not establish the complete path.
