## Judgment

Rangoon already has useful local content records, workflow definitions, export, offline integration evidence inspection, and operations observation vocabulary. It does **not** have a universal AI-systems wire adapter, connected LNSAT/OpenShell path, live authenticated ingest, managed proxy, or engine-issued authority. A small semantic interchange layer can make its modules composable **if it preserves native meanings and tracks loss**. Trying to flatten all protocols into one `allow/run/success` object would create false equivalence. The best near-term product is still the provider-independent local workbench; broad connected coverage is a measured expansion target, not a release prerequisite.

The prior direction that made an OpenShell middleware path owned by LNSAT is superseded. Rangoon should own only the adapter boundary and UI projection. OpenShell owns its native gateway/sandbox policy and observations. LNSAT owns its independent action authorization/approval/receipt/recovery evidence. Combining their observations in a graph is a correlation task; it is not a dependency or shared authorization transaction.

The market test is practical: can a developer import instructions, produce traceable revisions, compare exact capability changes, export a usable bundle, then understand which optional system actually controlled a later action? OpenShell's documented sandbox isolation and gateway controls are real native product areas Rangoon does not reproduce. LNSAT's exact-action authority and receipts remain a different product boundary. Rangoon's potential edge is a **clear capability lifecycle and loss-aware cross-system inspection**, measured on identical sanitized tasks with setup burden, preservation, coverage, latency and recovery evidence. No current test proves Rangoon has more features or stronger enforcement than either product.

## Product differentiation test

VUSL is Rangoon's proposed internal semantic layer, not a published community standard. Its value is avoiding false equivalence while linking a source capability revision to its compiled target artifact and, later, separately sourced runtime/authority facts. None of those individual techniques is exclusive. The **combination** is a product hypothesis that needs working vertical slices and user comparison, not a novelty or market-leadership claim.

| Existing product or standard | Existing overlap, evidenced by primary docs | Rangoon-specific job and proof still owed |
| --- | --- | --- |
| [LangGraph/LangSmith](https://docs.langchain.com/oss/python/langgraph/overview) | Graph orchestration, durable execution, human-in-loop, tracing, evaluation, prompts and deployment already exist. A node editor or runtime graph alone is not differentiation. | Preserve source-file spans and reviewed capability revisions across multiple export targets without adopting one orchestration runtime; demonstrate a provider-free source-to-export task. |

| [OpenRig](https://openrig.dev/specs) | Its AgentSpec/RigSpec/RigBundle formats, mixed-harness team daemon, startup layering and run records already cover portable agent/team configuration and operation. | [OpenShell](https://docs.nvidia.com/openshell/latest/about/architecture) | Sandbox, gateway, policy, credential routing and runtime controls are native. **What must be complete for the proposed product to matter:** one provider-free task must go from selected original files through detected candidate, human-edited/reviewed capability revision, explicit dependency and constraint preservation, target-specific compile/export, a real target load, and restart/readback to the same source spans. This is a vertical product workflow, not a claim that every pictured screen works. For every step, show source and revision identity, exact retained or changed bytes, user choice, failure/recovery state, and unsupported target behavior. The first optional connector then adds a second, independently sourced layer: intended capability scope versus native effective policy versus observed runtime events, without pretending one proves the others. LNSAT's separately qualified exact-action authorization/receipts can add a third layer later; it must not be required for the first two. Existing source-to-export pieces and an offline local operations window do not yet prove this full task on all three desktop OSs or any live cross-system linkage.

The possible distinction is **change-to-consequence traceability across independent products**, not a proprietary replacement for their formats or engines. Its concrete operator question is: “Which reviewed instruction became this target artifact, which native system evaluated the later request, what did it report, and where is evidence missing?” Rangoon earns that claim only after exact revision-to-export mappings, one qualified target loader, source-qualified observation joins, and task-based comparison. OpenRig's bundles, Langfuse's prompt-to-trace linkage, and OpenShell's OCSF records overlap parts of that chain; no broad uniqueness claim follows from this document. If the first source-to-export task is slower or loses required meaning, fix or narrow the workbench before adding more adapters.

**Coverage rule:** admit a new protocol family or adapter only when a named user task needs facts the current source-to-export or operator record cannot express, a pinned native contract can supply those facts, critical fields and loss are testable, and the UI can show unsupported, stale and unknown states without implying authority. The first release needs the provider-free capability lifecycle and one real target-load proof; it does not need generic adapters for every named standard. Later read-only OpenShell and LNSAT evidence must each answer a concrete operator question that the native product's own view cannot answer across the reviewed source and exported target. If an integration adds only a second place to inspect the same native log or policy, leave it native and link out. Do not count protocol breadth, connector logos or graph density as user value.

The first end-to-end user study should use one frozen sanitized project containing `AGENTS.md`, `SKILL.md`, a workflow and one target harness. **Baseline:** manual editing in one pinned editor build plus Git diff/revision tools, exporting to the same pinned target harness. **Rangoon arm:** exact same source snapshot, target, OS, allowed documentation, time limit and output criteria, with no engine installed. Freeze editor, Git, harness and Rangoon build IDs, corpus hash, task sheet and scoring rubric before enrolling participants; do not change them between arms. At least eight developers complete both arms in counterbalanced order on equivalent matched tasks. The required task is to inspect source spans, split/merge one capability, review the change, produce a loadable target bundle, restart and recover the exact revision, then identify source file/line/revision for a selected exported instruction. Capture elapsed time, successful target load, source-attribution correctness, silent loss, errors, clicks and ambiguous terms.

**Pre-set product gate:** every Rangoon output must load, with zero silent omission of required instructions and zero invented authority/effect; at least 90% of Rangoon source-attribution answers must be exact; median completion time must improve by at least 20% over the manual baseline without a lower task-completion rate. Report individual failures and distributions, not only averages. Missing the correctness gate blocks a usability claim; missing the time gate means streamline the workbench before expanding VUSL. This tests value against a real existing workflow, not superiority over LangGraph/LangSmith or Langfuse. Compare a named product only if its pinned release supports the identical task and conditions. A separate later task adds one pinned OpenShell read-only source and tests denied/allowed/changed/repeated/unknown facts; LNSAT follows only after its own gates. If measurable user value or traceability fails, narrow VUSL and product scope instead of adding adapters or graphics.

Do not build a replacement agent runtime, generic policy language, sandbox, trace backend or competing MCP/A2A/AG-UI protocol to manufacture a unique feature list. The competitive claim should be: **Rangoon helps author and compare portable agent capabilities, then shows exactly what optional systems reported and what remains unproven.** Even that remains a target until the task above passes.

The existing OpenShell combined-path type is the first clear migration example; leave it inert until a new independent contract is accepted.

**Source seam for the first connected operator record:** `crates/rangoon-integrations/src/descriptor.rs` and `inspection.rs` own closed synthetic I1 metadata and unverified fixture inspection. `openshell_runtime.rs` is a separate historical combined-path classifier that requires LNSAT fields; it is not an independent OpenShell decoder. `crates/rangoon-engine/src/lib.rs` is still the unavailable A1 port. This is a source audit and packet boundary, not a claim that O3 or either adapter exists.

## Gaps and risks, ranked

1. **P1 — Semantic authority collapse.** A generic `approved/allowed/succeeded` property could turn policy advice, UI action or provider response into dispatch authority. Require distinct stage types, source proof and negative conformance fixtures before any connected action.
2. **P1 — OpenShell combined-path inheritance.** Existing O1 input requires LNSAT grant/authorization ID even though new product direction requires separate connectors. Leave O1 inert and historical; design an independent v2 native OpenShell read-only profile. Do not silently rename its fields.
3. **P1 — Native payload and loss handling.** I1 can preserve bounded synthetic evidence, but no general opaque native-retention/round-trip/privacy contract exists for multimodal streams or future adapters. Define byte commitment, redaction and retention before claiming lossless translation.
4. **P1 — Export-to-effective-load discontinuity.** A generated bundle and a successful local export do not prove that a target harness installed or loaded those exact bytes. Even a matching loaded-artifact digest may leave effective layered configuration and instruction coverage unknown. Require one target-native loader/readback profile, distinct artifact identities and drift reporting before linking later runtime evidence to a reviewed revision. This is outside D0a's inert observation subset.
5. **P1 — Coverage, identity and direct bypass.** Neither connected ingress nor exact target-path custody is present. A green graph based on an API response would misstate mediation. Qualify source identity, path/credential custody and observed effect separately.
6. **P2 — Version/extension registry.** I1 is closed and safe but narrow. A broad language needs exact core/profile/extension negotiation and stale descriptor invalidation without replacing I1/A1/O1.
7. **P2 — Streaming and uncertain effects.** O1 handles ordered closed windows, but no provider stream/webhook replay/ack/reconciliation adapter exists. Preserve gap/duplicate/conflict and unknown terminal states.
8. **P2 — UI density and vocabulary.** Same graph can show authored workflow, provider topology and live observations only with distinct modes, source/status badges and drill-down. Avoid a single support meter or 3D animation that suggests all nodes enforce actions.
9. **P2 — Hosted/multi-tenant boundary.** Current desktop store and local host do not supply tenant-authenticated API, worker identity or shared secret management. VUSL is not a shortcut to hosted readiness.

OpenShell is the first **goal-specific read-only connector** because the requested operator record must explain an actual runtime boundary. This carries more integration risk than a Cerbos PDP read because it involves gateway/supervisor identities, native policy states and direct-path coverage; the D2 gate names those risks rather than hiding them. Cerbos remains the first low-risk generic policy-adapter candidate if OpenShell's exact release/read contract cannot be pinned. Neither is a prerequisite for the provider-free three-desktop workbench, and neither supplies LNSAT authority. D1 may proceed independently of D2.

For D2, [OpenShell v0.1.4 log documentation](https://docs.nvidia.com/openshell/v0.1.4/observability/accessing-logs) says its recent gateway buffer is finite and volatile, push can drop events, cursor resumption can report `OUT_OF_RANGE`, and supervisor, gateway and workload/runtime output have distinct collection paths. Its [OCSF export](https://docs.nvidia.com/openshell/v0.1.4/observability/ocsf-json-export) is best-effort and gateway JSONL does not archive supervisor lines. The pinned [TypeScript SDK](https://docs.nvidia.com/openshell/v0.1.4/sdk/typescript) documents a loss-aware `watchLogs` candidate, but its existence does not qualify Rangoon authentication scope, identity, collection completeness or a policy read. Therefore a connected Rangoon adapter must never label an unbroken execution history from one stream alone. Exact least-privilege access to each fact remains an implementation gate; documentation of an SDK, CLI or log path is not permission to run it or proof of adapter support.

## Acceptance and review checklist for later packets

- No provider: local import, manage, compose, compile, export and inspect stay usable.
- Every adapter row names exact product, protocol, adapter, semantic profile, environment, operation, evidence level, data classes and qualification date.
- Native bytes/IDs and provider-specific semantics survive or explicit loss prevents consequential use. Unknown critical extension rejects; optional unknown stays opaque/non-authoritative.
- Provider `allow`, guardrail pass, model advice, protocol negotiation, UI click and human authentication each fail negative tests that attempt to forge authorization or effect.
- Unavailable, unsupported, disconnected, error, stale, unknown and partially observed outcomes remain distinct in Rust/CLI/UI; no automatic retry after uncertain consequence.
- No hidden network, ambient credentials, provider installation or execution in offline tests; no source descriptions used as trusted instructions.
- Actual managed-proxy claim has route/credential custody, bypass analysis, provider-native execution-time checks and effect/reconciliation evidence for one named path.
- README and development ledger update with any future implementation/publication, preserving three-OS, encryption and local release gates.

## Open decisions

Human acceptance needed before public protocol, host/provider integration or consequential implementation: public VUSL name and whether it should be exported as a standalone standard; exact serialization and canonicalization; raw-native retention/erasure policy; first connected product/artifact; which provider-controlled consequence path, if any, merits Rangoon-managed proxy; and how to present a mixed reported/verified graph without suggesting enforcement. The authorized D1 offline parser does not grant those decisions. No comparison here establishes Rangoon has more implemented features than any competitor; the target is a better **qualified** cross-system capability map with honest loss and authority boundaries.
