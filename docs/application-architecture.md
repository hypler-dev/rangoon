## Internal operations-first boundary — October 22, 2026

The [accepted internal-first direction](intent.md#internal-operations-first-direction--october-22-2026) prioritizes Hypler's own supervised workloads over speculative integration breadth or a funding narrative. It extends the existing operations/fleet and deployment designs below; it does not replace the local capability workbench or create a second control plane.

Jeff's Customer Zero clarification preserves the general product: the same public contracts must work for another operator's projects, workers and providers through private configuration. The [source reconciliation](customer-zero-gap-analysis.md) distinguishes current content/model/inspection components from missing durable task service, runtime execution, MCP, worker and accounting functions. Its proposed distributed source-review pilot refines the next value milestone; the prior finite-read connector work remains independently useful without becoming a mandatory runtime or authorization dependency. A durable task must outlive its initiating Codex/desktop client, while actual scheduling and process isolation remain with a qualified runtime.

| Layer | Responsibility and boundary |
| --- | --- |
| Rangoon workbench and application services | Existing capability authoring/provenance/compilation, plus planned fleet supervision, typed task coordination, model-routing preferences, budget accounting and operator evidence. The same services should serve UI, eventual CLI and authenticated hosted APIs; the renderer owns no authority or database access. |
| Runtime, scheduler and monitoring adapters | Translate an explicitly supported operation to an established runtime's native interface. That runtime owns process placement, isolation and lifecycle; monitoring sources own their observations. A Rangoon placement recommendation is not a scheduler allocation, and a task acknowledgement is not a completed effect. |
| Independent authority integrations | LNSAT and alternative qualified engines retain their own authorization, approval, credential and evidence semantics. An unavailable required control blocks the affected operation, while unrelated local work remains available. OpenShell and LNSAT need not depend on each other. |
| Independent VUSL consumer | Future adoption of a pinned usable VUSL core preserves native identity, provenance, explicit uncertainty and translation loss. Rangoon does not maintain a competing VUSL specification or infer authority from semantic compatibility. |
| Managed application interfaces | IZIOS, Sugarberry and other portfolio systems may later expose versioned, allowlisted health/readback and narrowly scoped operational functions. These are candidates, not connected systems. No generic shell, shared application database or inferred production permission is introduced. |

The proposed orchestration core is an application-service responsibility within the modular architecture, not a mandate for a new daemon or microservice. Reuse the [shared management-state and deployment design](#deployment-tiers-and-distribution) and existing [fleet console](operations-control-plane.md#fleet-management-console-direction). A later server may own durable jobs, leases, outbox, scoped enrollment and task checkpoints; external runtimes still own actual scheduling. Do not build a competing scheduler or copy a desktop SQLite file across hosts. Neither LNSAT's nor VUSL's database becomes Rangoon's shared state.

Model routing and cost control need explicit resource/privacy requirements and provider-specific capabilities. Keep estimated, reserved, observed and finalized usage distinct; missing usage is unknown, not free. Concurrent admission, retries, reservation settlement, cancellation and late provider charges need a reviewed accounting contract before a hard budget limit is claimed. Local CPU/GPU time, memory, energy estimates and external API charges have different measurement bases. No model or tool can expand its own budget or authority.

Proxmox, Nomad and other established infrastructure products are integration candidates, not a required combined stack or current compatibility claim. Select a product/version, supported OS/backend, license and exact operation only when a pilot needs it. The supplied hardware list is not an authenticated inventory; older GPU acceleration and usable capacity require measurement. Keep production hosting outside the experimental worker pool and establish network, identity and resource isolation before enrollment. No inventory scan, provider installation, runtime activation or production access is authorized by this architecture.

The user interface stays layered: searchable inventory/table first, compact task/status bar, then a selected-system inspector; topology remains an alternate view. Show source, freshness, unsupported operations and unknown outcomes at the point of action. Fleet, Tasks, Deployments and Evidence reuse the existing Operations group; budgets appear with their task/project scope rather than as decorative totals. The next delivery sequence is in the [canonical plan](plan.md#internal-operations-first-delivery--october-22-2026).

## Purpose and first useful outcome

Rangoon should turn scattered agent instructions into understandable, reusable capabilities, then make the change from an idea to a deployed or executed action inspectable. Its first useful promise is: **know what an agent is configured to do, where those instructions came from, and what a proposed change will preserve or lose.** That is valuable without a running LNSAT engine, a model account or a cloud subscription.

The supplied images describe a connected product lifecycle, not twenty unrelated dashboards. Import, Decompose, Merge/Split, Skills and Workflows should operate on the same versioned records. Command Center summarizes those records and real operation states. Connectors expose precisely available operations and authority boundaries. Test Lab, Compile, Deploy and Audit should show the actual evidence produced by their respective services. Sample numbers and decorative graphs must give way to useful empty, unavailable and recovery states as each real service arrives.

The accepted October 7 [product-value priority](plan.md#delivery-priority-demonstrate-product-value-before-expanding-infrastructure) puts usable local refactoring and export ahead of additional disconnected scaffolding. Preserve current optional-provider/operations contracts, but connect them only through reviewable user outcomes. The source-implemented [export handoff](export-handoff.md) reuses the strict bundle verifier; actual target-loader qualification and attributed model-proposal application remain separate gates. The accepted E1 priority now controls the next implementation slice, as clarified in the [delivery plan](plan.md#delivery-priority-demonstrate-product-value-before-expanding-infrastructure). No new runtime, authority or platform support is inferred.

## Core decisions

1. **One modular application, three desktop operating systems.** Keep the existing Rust domain/services and scoped Tauri host. Evolve the current vanilla-JS workbench into a shared typed UI incrementally when the revision editor needs it; a framework rewrite is not a prerequisite for useful features. No second desktop shell or separate Windows product.
2. **Content management is independent of execution authority.** Rangoon owns source, assets, review, composition, compatibility, jobs and their presentation. LNSAT is a separate product and optional authority/evidence integration. External providers retain their own identity, authorization, enforcement and operational semantics. No absent, disabled or failed integration may block local startup, reading, authoring, decomposition, composition, revisions, comparison, compilation, export or inspection.
3. **One authoritative record per concern.** Immutable source and asset revisions in Rangoon; authority decisions and consequence evidence in LNSAT or another explicitly qualified provider. The graph, counters, search index and UI are derived views. Never use an engine database as a shared application database.
4. **Ports precede integrations.** Format importers, compilers, analysis providers, connectors, execution targets and authority providers have separate interfaces. Their availability and tested capability subsets are explicit. A logo, credential or installed package does not imply an operation is supported or authorized.
5. **Build safe content work now; qualify integrations separately.** A1 provides honest unavailable functions. It does not recreate LNSAT with a permissive mock. The first neutral integration packet uses only offline fixtures; each later adapter has its own product/version/capability and privacy qualification. Provider allow is not Rangoon approval or execution permission. Broad integration coverage is not a local workbench release gate.

The October 16 [independent-connectors decision](provider-interoperability.md#independent-engine-connectors--october-16-2026) keeps LNSAT and OpenShell as separate optional Rangoon integration targets. OpenShell's native sandbox-policy and execution observations do not inherit LNSAT authority, and LNSAT's request/receipt path does not require OpenShell. The older LNSAT-owned OpenShell middleware candidate is historical research. Existing A1/I1/O0 source is unchanged until a separately reviewed, versioned source packet replaces any combined-path fixture.

The proposed [universal systems language](universal-systems-language.md) is a loss-aware semantic projection **over** these existing ports and records, with an [implementation audit and capability matrix](universal-systems-audit.md). It does not replace provider-native protocols, issue authority, introduce a new store, or move the local release gate. This design is not yet an accepted source contract.

The October 13 [scoped support direction](provider-interoperability.md#scoped-support-commitments) qualifies specific adapter operations and deployment paths. Common ownership makes Rangoon plus LNSAT the strongest end-to-end assurance candidate, not a current guarantee; all live adapters remain unqualified. External providers retain their responsibilities. Replacing providers requires a loss-aware preview and refusal when mandatory controls are missing. [Coverage/control-assessment colors](operations-control-plane.md#coverage-and-control-assessment-presentation) explain scoped evidence independently of availability and authorization.

## Approval, telemetry and live operations are core

The October 7 accepted [operations control-plane contract](operations-control-plane.md) adds approval management, redacted correlated telemetry and dynamic graph/timeline/replay as core product surfaces. Rangoon manages configuration and routing; a selected qualified authority engine issues scoped authorization and a trusted execution path checks it at consumption. Human and bounded delegated-agent stages cannot bypass policy or mandatory human duties. Delegation cannot self-expand. Keep per-operation enforcement coverage explicit across systems and engines.

Build inert application records/projections first, then local operations views and bounded read-only ingestion, followed by one qualified enforcement path and cross-system/hosted conformance. The graph and approval inbox are derived projections; they cannot issue authority. Telemetry, verified engine evidence and actual execution outcomes remain distinct. These stages are planned; A1 stays unavailable and no live collector, approval service or executor is introduced by this architecture update.

## Records and state transitions

| Record | Identity, ownership and rules |
| --- | --- |
| Source snapshot | Current R2a identity binds basename and exact bytes; immutable, original digest retained. No absolute path is saved. A source digest is not authenticity or permission. |
| Project | Future stable ID grouping source references, target adapters and local preferences. A project is not a filesystem grant or tenant. Root bindings need their own explicit selection and revocation. |
| Proposal | Candidate extraction, split or merge with exact source spans, generator version and unresolved coverage. It can be rejected without losing the source. |
| Capability and revision | Stable capability ID plus immutable revision. Content, dependencies and requirements have independent review state. Review records who accepted a particular revision; it does not approve execution. |
| Provenance edge | Exact input revision/span to output revision, derivation type and tool version. Every edit retains its inputs; deleted/unassigned source is visible. |
| Content composition | Exact source/capability revision ranges, ordered authored/replacement pieces, coverage and explicit skill destinations. Its editable graph projects existing recipe records. |
| Workflow definition | A distinct versioned graph with exact capability revisions, control paths, typed data mappings, branches and human checkpoint declarations. W1 validates structure; later saved workflow identity/revisions remain independent from run state and execution authority. |
| Compatibility report | Target/version/adapter digest, preserved/adapted/unsupported concepts, diagnostics and tests. Unsupported security-sensitive meaning blocks compilation. |
| Bundle / export plan | The implemented bundle holds a canonical manifest, exact artifact bytes, component lengths and a checksum of preceding bytes; local Export re-resolves and recompiles after picker selection before exclusive plaintext creation, and external Inspect opens no workspace. Inspection also reports the whole-file digest. Destination grants and expected existing state belong to future export/installation plans. Export and activation are separate operations; checksum and identities establish internal consistency only. |
| Job / attempt | Stable job ID, input revision, attempt ID, cancellation request, lease, state and result references. The next attempt is a decision, not an automatic consequence of a timeout. |
| Engine evidence reference | Provider identity, exact external ID, contract version, observation time, integrity/freshness status and bounded raw evidence. Do not convert an app cache into an engine-issued receipt. |

Content lifecycle: `source snapshot → proposal → reviewed capability revision → pinned composition → validated bundle → explicit export`. An edit creates a new revision and invalidates dependent validation; it does not mutate the previous reviewed revision in place. A comparison can explain additions, moved spans, exclusions and unresolved conflicts before acceptance.

Execution lifecycle is separate: `planned → awaiting engine decision → awaiting human approval if required → eligible for bounded consumption → submitted → succeeded / failed / outcome unknown`. These are conceptual states until the exact engine contract is bound. “Approved” is never a synonym for “executed.” Unknown effect requires reconciliation; a crash, cancellation or lost response cannot be presented as proof that nothing happened. No automatic retry of consequential work after an uncertain outcome.

### LNSAT 1.0 intake checklist

1. Identify the actual signed/reproducible supported artifact, source commit, license, supported OS/architecture and dependency provenance. A tag or README alone is insufficient.
2. Compare product, wire and feature-surface contracts with the pinned reference. Record removed/changed fields, routes, errors, session and consequence semantics. Use exact accepted compatibility, never guess from semver or silently downgrade.
3. Implement one adapter behind the port with operation-specific types. Keep engine-issued opaque IDs and original evidence; do not normalize away authority-critical distinctions. No generic URL/request escape hatch.
4. Qualify peer identity, transport, expiry/rotation/revocation, native secret custody, redaction and unavailable-store behavior. Loopback and a desktop process are not by themselves authentication. Do not reuse withdrawn UDS or ambient cookies.
5. Run contract fixtures and real isolated integration tests per supported operation and OS. An installed engine, healthy endpoint or successful read does not enable writes.
6. Enable exact read-only capabilities first. Require independent end-to-end consequence and recovery evidence before A4. No public/prod target is needed for this qualification.
7. Publish a capability matrix with tested engine artifact, adapter version, target OS and evidence. Show stale or incompatible states explicitly. Keep local content management available during engine outages and upgrades.

## Composition boundary and service extraction

The current composition path is a useful test of the proposed modular monolith. The renderer builds an editable recipe, receives a host preview, and validates its display shape and byte mappings. The native command accepts bounded raw IPC and retains a private, single-attempt preview handle. `rangoon-store::Workspace` resolves saved source/revision references and current destination heads, calls the pure `rangoon-compose` transformation, and checks saveability. At commit it opens an immediate transaction, reloads records, compares the retained state and recomputed preview, writes the resulting revisions, then checks the stored state before returning a receipt. A renderer-provided preview body, original bytes, or filesystem path cannot be substituted at commit. See [native composition](composition-native.md) for the exact wire and failure behavior.

This boundary is sound for the local workbench, but two seams need deliberate maintenance:

| Seam | Current risk | Required control |
| --- | --- | --- |
| Renderer preview checks | JavaScript independently checks materialized text, mappings, coverage shape and reported `saveable`. ## Capacity model for a 500–1,000-person organization

Capacity must be specified by operation, not by an undifferentiated "request" count. A capability edit or export, a hosted API read, an observed agent action, a telemetry event, an authority-engine decision and a live-graph update have different cost and ownership. Rangoon is not on the execution-time authorization path: an engine must continue to enforce its own rules if Rangoon is slow or unavailable. Rangoon configuration changes become effective only through each target's qualified admission and readback path. Operations views may lag, but must show their source watermarks, lag and gaps rather than imply current completeness.

**Proposed qualification workload, not measured capacity or a release claim:** one large tenant with up to 1 million observed actions per day, a 60-second burst at 1,000 actions/second, and a synthetic planning factor of 10 minimized evidence events per action. That implies 10 million events/day and a 60-second burst at 10,000 events/second. At a *hypothetical* 1 KiB persisted event, raw event bodies alone consume about 9.5 GiB/day and 286 GiB per 30 days, before indexes, native evidence, replicas and backups. Payload-size distribution, tenant count, retention and concurrent readers must be measured before sizing a deployment. Sustained 1,000 actions/second would be 86.4 million actions/day and needs a separate scale tier and proof. A desktop selected-file O1 window, capped at 1,024 events and 2 MiB input, is an inspection unit, not a million-event ingest service.

The hosted path should use admission with authenticated tenant and producer identity; bounded validation and redaction; a durable partitioned event log or equivalent append contract; idempotent, version-pinned projections; and paged query/subscription APIs. Partition by tenant and stable producer/stream identity so causal order has a defined scope; never claim a global total order. Separate immutable native evidence references from minimized searchable fields. Batch writes and projections where safe, but never combine distinct attempts or drop required evidence to improve throughput. Per-tenant quotas and fair scheduling prevent one fleet from exhausting other tenants. Bounded queues, explicit backpressure/retry signals, producer cursor checkpoints and replay make overload observable. On crash, retry or partition, duplicate identity with different bytes is a conflict; missing ranges and retention gaps remain visible. An ingestion acknowledgement means only the stated durability stage, never authority verification or completed execution.

The local desktop remains a bounded single-user workbench. It may inspect paged or sampled *views* of a larger hosted history after a qualified connection, but evidence capture itself cannot be silently sampled. Do not route millions of events through one Tauri IPC response, one SQLite transaction or the renderer's graph state. Keep graph layout and animation downstream of bounded projections, with stable selection and a table/timeline fallback. A future service may scale ingest, projection and query workers independently while reusing domain contracts; that extraction requires explicit tenant context, storage and recovery tests rather than a raw HTTP wrapper over desktop commands.

Before advertising this capacity, run reproducible load tests with pinned hardware, payload distributions, event/action ratios, tenant counts, retention and fault profile. Report sustained and burst throughput separately; p50/p95/p99 ingest acknowledgement, projection lag, API reads and memory; queue depth; storage amplification; retry/duplicate/conflict rates; and lost or unaccounted event ranges. Include 72-hour soak, disk-full, worker crash/restart, slow subscriber, hot tenant, late/out-of-order producer and tenant-isolation cases. Set latency SLOs from a measured pilot and an agreed durability point; no current source or test establishes these targets.

**RM-1 internal offline contract — October 27, 2026.** Jeff's request to implement the direction accepts the [seven-path source packet](intent.md#rm-1-offline-inventory-implementation--october-27-2026). **BF-2a retained-root source — October 27, 2026.** The host crate now implements unmounted Unix metadata traversal in `source_inventory.rs`, using the already locked/cached `rustix =1.1.5` safe filesystem API. `rangoon-host` retains `#![forbid(unsafe_code)]`. This direct dependency edge and fs feature are new; no package version/checksum changes or downloads occur. The pinned crate has the existing Apache-2.0 WITH LLVM-exception OR Apache-2.0 OR MIT license expression; dependency checksum/lock evidence is in the development receipt, not a security certification.

A caller must supply a fresh native-selected absolute root, never renderer paths. The backend walks from `/` with retained directory descriptors, `statat(SYMLINK_NOFOLLOW)`, `openat(DIRECTORY|NOFOLLOW|NONBLOCK|CLOEXEC)` and pre/post device/inode checks. It refuses root `/`, relative/parent paths, symlink ancestors/final roots and excessive root-component depth. Root ownership means the opened directory object: renaming its pathname and replacing that pathname with a symlink does not redirect the existing owner. There is no canonicalization, `/proc` reopening or path-string containment test in production. This is an unmounted host API, not enforcement that a frontend request came from a picker.

Enumeration stays relative to owned directory handles. Only directories are opened; regular/special files receive no-follow metadata inspection only. Child identity is checked after opening; cross-device/repeated directories and detected replacements are refused and reported. Same-device mount aliases and a compromised kernel/privileged host are not isolated by this API; tests use no real mounts. Metadata may change immediately and directory iteration is not an atomic snapshot. Previously returned pages remain copies held by callers; a later native admission/renderer owner must purge/fence those copies on lock or revocation.

Pages return at most 50 rows after at most 512 visited entries; a session stops at 10,000 visited entries or 1000 emitted rows, with depth at most 16 below the chosen root. Directory handles are bounded by traversal depth and identity/path sets by the session budgets. Exact relative Markdown names, byte lengths, whole-second filesystem mtime in milliseconds and session-local observation ordinals are returned. Ordinals are neither durable file references nor revision ancestry. There is no file content, hash, native absolute path, device/inode, key or original in serialized rows. Reading a selected row later still needs retained native content custody; a display path must never become an arbitrary read endpoint.

The initial discovery policy excludes dot entries other than `.claude`, `.cursor`, `.windsurf`, `.github`, `.codex`, `.agents`, plus `node_modules`, `target`, `vendor`, `dist` and `build`. It rejects invalid UTF-8 names, unsafe separators/control/format/reserved names, overlong segments/paths and non-ASCII characters outside the initial alphanumeric subset. Unicode sequences are never normalized; this backend is deliberately narrower than RM-1's offline path grammar, and unsupported names produce an explicit partial reason. Other file types, symlinks and special files are excluded without reading them. Future configurable ignore rules need a reviewed policy contract, not ambient shell/git execution.

`exhausted` means traversal stopped, not complete coverage: cumulative partial reasons separately retain read/replacement/device/loop/name/depth/entry/record problems. Work-limited short/empty pages remain resumable. Duplicate relative observations are refused. Cancellation before/through/after a page drops traversal handles and discards the whole current page; explicit close is terminal. The current callback can stop subsequent work, but cannot promise interruption of a blocked kernel call or a hard elapsed-time limit, especially on a selected network filesystem.

### Deployment management as a control-plane workflow

Separate three deployment objects: a Rangoon service version, a compiled capability/artifact revision sent to a target harness, and an authority-engine configuration revision. One successful deployment does not establish the other two. A proposed managed target has an enrolled identity, owner, environment, adapter/product/version pin, allowed operation subset, current observed/effective revision, health and rollback capability. An imported or qualified discovery result creates only an unverified review candidate, not registered inventory or deployment permission. Active discovery requires explicit consent, an allowlisted destination and scope, bounded rate and egress, recorded provenance and a separately qualified adapter; authenticated enrollment and operator review precede managed status.

The operator path is **draft -> compile and loss report -> target-specific validation -> review/required human approval -> staged plan -> canary -> wave rollout -> target-native readback -> observed effective state -> monitor/reconcile or rollback**. Rangoon's deployment approval authorizes only its own orchestrator under its own qualified identity/role rules; it is not an engine authorization, execution receipt or proof of effect. A deployment plan pins exact artifact bytes/digest, target set, expected prior revision, approval and expiration, rollout order, concurrency/failure budget, health/evidence criteria and rollback artifact. Target workers use least-privilege outbound enrollment or a separately qualified authenticated adapter. A durable job and transactional outbox preserve intent across restart; per-target leases and expected-revision checks prevent competing rollouts. Automatic retry is limited to proved idempotent preparation/read operations; an uncertain consequential write pauses for native readback or human reconciliation. Rollback is a new explicit operation, not proof that previous effects vanished.

Show `planned`, `queued`, `admitted`, `sent`, `acknowledged`, `installed`, `effective`, `partially effective`, `failed`, `unknown`, `rolled back` and `unmanaged` at **each target**, with native evidence and freshness. A healthy endpoint or transport ACK is not effective configuration. A wave with one failed or unobserved target remains partial; dashboards must not compress it into a green fleet state. Initially, these are architecture and UI contracts over absent deployment adapters. No current Rangoon source deploys capability or authority revisions to live remote endpoints.

Keep default Deploy screen task-focused: selected artifact and target group, compatibility/loss summary, next wave, per-target status and one clear action or recovery path. Open advanced details for exact digests, native receipts, cursors, retries, leases, routing and storage diagnostics; expose equivalent scoped CLI/API operations for operators. Fleet topology can add a graph, but the table and target inspector remain authoritative for precise state and keyboard use. An unavailable adapter or unqualified deployment operation stays disabled with a reason, while local compile/export remains usable.

The [Fleet management console](operations-control-plane.md#fleet-management-console-direction) supplies the vSphere-like inventory, task and per-instance inspection direction without replacing the local capability workbench. Rangoon may manage only operations proved by each adapter and target contract; a shared fleet view is not a shared authority engine.

## Proposed identity step-up for sensitive human approvals

October 9 question from Jeff: could 2FA strengthen approval authority, and what issues would it introduce? Recommendation, not an implemented/accepted authentication contract: require fresh phishing-resistant authentication through a qualified identity service for selected consequential human approvals. Prefer appropriately verified WebAuthn/passkeys or hardware authenticators, with explicit enrollment, revocation, lost-device/recovery and unavailable-provider handling. [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html) distinguishes authentication assurance and step-up; [WebAuthn](https://www.w3.org/TR/webauthn-3/) supplies public-key authentication primitives. No AAL or certification claim follows from selecting a method.

Authentication verifies the claimant; it does not grant a role, constitute the approval decision or bypass execution checks. A later approval contract must bind authenticated approver identity/session, exact request/material digest, policy revision, scope, expiry and replay-resistant challenge. A WebAuthn assertion is not automatically a signed transaction summary or proof of human understanding; a qualified server-side approval presentation and association is still required. Recovery must not silently weaken mandatory duties or create ambient authority. Agents cannot satisfy a designated human step-up with their own credential. Provider-specific MFA and approval support need separate qualification. Step-up should apply to designated sensitive approval duties, not ordinary local capability authoring, comparison or composition. Core Rangoon workflows must remain usable without an identity provider; an unavailable required authenticator blocks that protected approval only and cannot silently downgrade its assurance. The current local authority planner stores no authenticators and displays no protected/verified badge.
