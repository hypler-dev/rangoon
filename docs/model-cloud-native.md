# Native cloud model assistance

Authority: the accepted October 6 model-assistance continuation in [intent.md](intent.md). This contract refines [cloud request custody](model-cloud-session.md), [credential custody](model-cloud-custody.md), and the [cloud adapter](model-cloud-adapter.md). Implementation is in progress; current publication and evidence belong in [development.md](development.md). No native cloud-send capability is claimed until that evidence exists.

## Operation ownership

One native model-operation gate serializes local and cloud preparation, connection checks and sends. Profile configuration also takes the gate briefly; clear/cancel remain available while busy. Workspace reads retain their existing separate guard. Native cloud credential use additionally acquires the same custody slot used by inspect/save/remove, so those operations cannot replace an in-use credential in this process. This is not an interprocess OS-store lock.

Blocking workspace/OS callbacks retain their operation leases until they actually finish, even if the awaiting IPC future disappears. An outer drop guard cancels the associated operation promptly. Native dialog callbacks own their completion/cleanup, rather than relying on the IPC waiter to perform cleanup after an await. Pending OS prompts retain their parent windows and operation leases until the callback ends. Clear, close and cancellation cannot resurrect a staged request or release a busy slot while a retained callback still owns it.

The portable cloud session gains a resolution lease before any OS read. Its closed saved-ID selection is validated and old preparation invalidated first. The worker reads only the fixed app-owned OS slot, validates its entire envelope, and prepares with the actual revision. The native host retains that full zeroizing envelope with the resulting prepared handle/request ID. No key, key fragment or key fingerprint is serialized. Selected source content may itself contain secrets; this feature does not redact it.

The native staged envelope and portable preparation are coordinated under one short native state lock. Clear/configure/new preparation invalidate both together. A send consumes both identities once; mismatched, missing or stale envelope/request pairing cannot be retried. Native source resolution and OS calls occur outside that state lock. A cancelled/cleared resolution cannot install a late envelope. Staged secrets are session-only and drop on replacement/clear/process exit; memory erasure of all runtime/library copies is not guaranteed.

## Commands and consent

Main-only commands are `get_cloud_model_profile`, `configure_cloud_model`, `clear_cloud_model`, `prepare_cloud_model`, `check_cloud_model`, `send_cloud_model`, and `cancel_cloud_model`. Profile inspection/configuration performs no OS-store or provider access. Prepare accepts only the bounded cloud saved-ID selection, reads the OS slot explicitly, and makes no network request. Send accepts only the 512-byte closed prepared-handle/request-ID pair. Check accepts an empty object and uses the configured profile; it contains no saved source.

Every response has exactly `schemaVersion: rangoon.cloud-session-result.v1`, `generation` (canonical nonnegative decimal string, or null if state is unavailable), `runId` (null before acquisition, otherwise `cloud-run:` plus 64 lowercase hexadecimal characters), `authority: none`, `outcome`, and only the fields specified below. Async responses retain the captured generation/run, never a newer run's identity. Inspection does not poll the OS store.

| Outcome | Additional fields |
| --- | --- |
| `unconfigured`, `configured`, `cleared`, `cancel_requested` | `session`: published cloud `SessionView` |
| `prepared` | `prepared`: published cloud `PreparedView` |
| `checked` | `check`: cloud `CheckResult` |
| `completed` | `completion`: cloud `Completion`; `freshness`: `current`, `stale`, or `unavailable` |
| `cancelled` | none |
| `failed` | `code`: one closed code below |

Closed session/native codes are `invalid_request`, `invalid_profile`, `unconfigured`, `busy`, `session_unavailable`, `stale_prepared`, `run_not_found`, `input_unavailable`, `input_empty`, `input_stale`, `pack_invalid`, `pack_over_budget`, `workspace_busy`, `confirmation_unavailable`, `credential_unavailable`, `credential_missing`, `invalid_stored_credential`, and `credential_changed`. Closed transport codes additionally include `profile_mismatch`, `invalid_credential`, `request_over_budget`, `timed_out`, `connection_failed`, `address_rejected`, `tls_rejected`, `redirect_rejected`, `remote_rejected`, `response_too_large`, `response_invalid`, `response_incomplete`, `response_refused`, and `proposal_invalid`. Cancellation uses outcome `cancelled`. No dynamic error text, provider error body, source text, or key material occurs in failure responses.

Every main handler checks the injected `main` WebView label. Configure/prepare/send/cancel require raw JSON bytes, capped at 1,024/8,192/512/256 bytes respectively, with the existing closed cloud schemas. Get/clear/check require an empty structured object. No renderer-selected OS service, account, URL, credentials, body, or approval fields are accepted.

An isolated bundled `cloud-model-confirmation` window receives only cloud review/get/confirm/cancel commands. Its closed decision binds the active cloud run and exact request ID. A single-use native consent slot rejects duplicate/stale decisions. Main-window IPC cannot supply an approval boolean. The child displays fixed origin, model, purpose, method/path, credential revision, exact outgoing body or no-body metadata check, byte length/digest, source dependencies and pack ID where applicable. Cloud-specific schema tags and handles cannot be accepted as local consent.

The `cloud-model-confirmation` capability grants only `get_cloud_model_review`, `confirm_cloud_model_review`, and `cancel_cloud_model_review`. Main has none of these permissions. Each handler checks the injected child label; structured invoke arguments cannot impersonate it. The child loads only bundled `/cloud-model-confirmation.html` with no query, fragment, credentials or port, rejects other navigation, and retains the IPC-only CSP with no network/filesystem/window/event/shell permissions. Dynamic values use inert text, never HTML or navigation.

- `get_cloud_model_review` requires an empty object. Ready response has exactly `schemaVersion: rangoon.cloud-review.v1`, `outcome: ready`, `authority: none`, `generation`, `runId`, `requestId`, `purpose` (`analysis` or `model_check`), `origin`, `model`, `method`, `path`, `credentialRevision`, `bodyBytes`, `bodySha256`, `bodyJson`, `packId`, and `inputs`. Check uses empty body string, zero bytes, empty-body digest, null pack ID, and empty dependencies. Unavailable response has only schemaVersion/outcome/authority.
- Confirm/cancel require at most 512 raw bytes with exactly `{schemaVersion:"rangoon.cloud-review-decision.v1",runId,requestId}`. Run ID is `cloud-run:` plus 64 lowercase hex characters; request ID is 64 lowercase hex. Reject unknown/duplicate fields, trailing JSON, local schemas/handles, stale IDs, and duplicate prompt claims. There is no `approved` field.
- Decision response has exactly `{schemaVersion:"rangoon.cloud-review-status.v1",outcome:"finished"|"unavailable",authority:"none"}`. It grants no transfer authority. Invalid/stale decisions cannot affect another run. Confirm claims one prompt and resolves its decision only after the OS dialog exits; cancel resolves false immediately only if no prompt is active. A pending prompt retains custody and defers window destruction until callback cleanup. Cancellation, owner drop, or close prevents a later affirmative answer from reviving the run.

Final affirmative authority comes only from a parented native OS dialog. For analysis it says that selected text and the stored credential will be sent to OpenAI; for a source-free check it says the stored credential and model identifier will be sent, with no selected source. Both name the fixed origin/model and request ID. Saving a credential does not approve a transfer. The review UI explains unknown cost/retention/region, that `store: false` is not Zero Data Retention, and that cancellation cannot recall dispatched data or establish zero cost.

Both analysis and the source-free check hold identical credential custody through consent, re-read, dispatch and completion. Analysis claims the retained prepared envelope. Check first acquires its operation and credential-use leases, reads the full OS envelope, and constructs its immutable `CheckRequest` with that envelope's revision before installing consent. A check never borrows consent or credentials from a previous analysis or check. After affirmative native consent, it reads the OS slot again and compares the complete retained envelope, including both revision and secret bytes. Same-revision altered secret, deletion, corruption or unavailable OS store blocks transfer. Only the validated current envelope can be converted into an opaque zeroizing transport credential. No renderer credential getter or environment-key fallback exists. The unavoidable out-of-process replacement/revocation race after the comparison is not hidden.

Immediately before transport, the host checks cancellation/generation and input freshness under the workspace guard. Stale or unavailable saved inputs block analysis. A post-response freshness read labels the advisory result; failure to read becomes unavailable, never current. These reads observe points in time and cannot prevent another process changing SQLite after a read. Transport always uses the retained snapshot bytes, never a rebuilt renderer request. No result applies changes, grants review/approval, executes tools or activates LNSAT.

## Source-free cloud check

A separate immutable `CheckRequest` binds the cloud profile, credential revision, fixed origin, `GET`, path `/v1/models/{model}`, empty-body SHA-256 and zero body bytes. The already constrained model identifier contains only ASCII alphanumeric/dot/underscore/hyphen and starts alphanumeric, so it cannot inject path/query/header syntax. Identity uses domain `rangoon.cloud-check-request.v1\0`, big-endian u64 canonical binding length, and binding JSON. It contains no source/pack and does not inspect credentials on construction.

`CloudClient::check` requires the same revision and shares the process-wide cloud flight guard, fixed-name TLS, public-address classifier, proxy/redirect/retry denial, cancellation and 10-second DNS/TCP/TLS deadline with analysis. Its total deadline is 30 seconds and its JSON body cap is 65,536 bytes. GET sends no body; no credential or revision occurs in the path. Only an HTTP 200 model metadata object is accepted. Preflight the bounded JSON using existing depth/count/duplicate limits; require `object: model`, bounded nonblank printable `id`/`owned_by`, and nonnegative integer `created`. Optional nullable `shutdown_date` is validated as an ISO calendar date. Bounded additional metadata is ignored and never echoed. Require the returned ID to equal the explicitly requested model; a different identity fails closed rather than silently changing the selected model. Non-200 bodies remain unread and produce closed failure diagnostics.

A check receipt binds request/profile/revision identities and the exact response-byte digest, reports provider-declared model/owner/creation/shutdown metadata, and states `model_visibility_only`, unknown inference compatibility/cost/retention/processing location, and authority none. Success is not proof of Responses compatibility, quality, context capacity, production readiness or zero provider processing. Analysis and checking have independent consent; a passed check cannot approve an analysis.

The official [model resource reference](https://developers.openai.com/api/reference/resources/models), [OpenAI OpenAPI document](https://raw.githubusercontent.com/openai/openai-openapi/main/openapi.yaml), and [Python SDK model type](https://github.com/openai/openai-python/blob/main/src/openai/types/model.py) were inspected October 6, 2026 for GET/bearer/200 metadata behavior. The endpoint documents 403 and 404 responses, but their exact error-component reference resolution remains open and is unnecessary here because error bodies are not decoded. Byte/deadline limits above are Rangoon limits, not provider guarantees.

## Workbench and qualification

The existing Model Assistance surface gains an explicit Local endpoint / OpenAI cloud route selector, separate session profiles, and shared saved-record/payload/result interaction. Cloud origin is fixed and not editable. Credential management stays a separate explicit action; page load and route switching do not inspect the OS store or contact a provider. Prepare, check and send are explicit actions. The isolated confirmation window uses the existing visual tokens, inert escaped text, visible keyboard focus, responsive layout and reduced-motion support. All outputs remain advisory; application controls stay unavailable until the separate proposal-to-draft feature is implemented.

Qualification requires shared-lock contention/drop tests, credential full-envelope same-revision tamper/missing/unavailable tests, stale request/decision rejection, generation/close/cancel and pending-dialog cleanup, source-free GET exact bytes/auth/TLS/error/cancel tests, strict metadata decoding, UI/controller schema/state tests and synthetic rendered/native QA. Native tests must use disposable fake stores and synthetic transport; ordinary tests never inspect existing OS credentials or call providers. GUI tests may use a fresh isolated synthetic slot and cancel the final network decision. Any actual approved GUI cloud-network proof requires a separately authorized synthetic test mechanism or provider test. Source/native build CI remains distinct from all-three-OS interactive and release qualification.

## Delivery split

The first implementation portion supplies the immutable source-free check and strict transport decoder, pre-credential resolution leases, and shared native operation ownership with local dialog/drop hardening. Native cloud command registration, credential-use orchestration, the cloud review window, and route-selection UI remain subsequent work under this contract. Merely compiling the portable check does not enable cloud sending in the desktop. Each portion requires separate named validation and independent review in the development ledger.
