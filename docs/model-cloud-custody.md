# Native cloud credential custody

Authority: the accepted October 6 model-assistance continuation in [intent.md](intent.md). This is the implementation contract for the M1c credential-custody slice. The slice itself makes no provider request; separate native cloud orchestration now consumes its custody under explicit consent. OS and provider qualification remain incomplete. Evidence belongs in [development.md](development.md).

## Outcome and scope

The operator can explicitly inspect, create/replace, and remove Rangoon's single OpenAI credential slot. This slice makes no provider requests and neither tests key validity nor grants permission to transmit source. The local model workbench remains independent. Separate native cloud orchestration binds credential revision, fixed HTTPS origin, exact selected payload, model and final native send consent; saved credentials alone grant no transfer authority.

No secret store is accessed at startup or by passive polling. Inspection is an explicit action and returns only provider, custody backend, state and a random revision reference. No key, key fragment, key hash or arbitrary OS-store attribute is returned to a renderer. Only the application identifier plus a fixed versioned OpenAI service/account determine the slot. Renderer input cannot select a service, account, path, backend, origin or provider. No credential enumeration, shell command, environment-variable discovery, existing-account import, plaintext fallback or session fallback exists.

## Stores and protected material

Use pinned `keyring-core` 1.0.0 with an explicitly constructed store, never its global default or mock/sample stores in production:

| Target | Backend | Configuration |
| --- | --- | --- |
| macOS | `apple-native-keyring-store` 1.0.2 | User/login Keychain, `keychain` feature |
| Windows | `windows-native-keyring-store` 1.1.0 | Credential Manager, explicit Local persistence |
| Linux | `zbus-secret-service-keyring-store` 1.0.1 | Secret Service with `crypto-rust`; absence/lock/access denial fails visibly |

The Secret Service adapter explicitly negotiates a DH-encrypted session with the service; this does not attest encryption of its backing files. The native desktop dependency workspace remains separate from the portable Rust 1.85 core. An OS store can prompt for access or unlocking; OS calls may block and are not claimed to support cancellation or a deadline. One custody operation owns the slot until its worker finishes. No overlapping access or automatic retry is allowed.

Store one bounded binary envelope: fixed format marker, 32 random revision bytes, and 1–2,048 ASCII graphic bytes for the credential. Reject whitespace, controls, non-ASCII, empty and oversized credentials without echoing input. Do not assume a provider prefix such as `sk-`. The secret and revision reside together in the OS store; no sidecar or SQLite credential record is written. Fresh replacement gets a fresh random revision. Native secret buffers use zeroizing ownership; no secret-bearing type implements Debug or Serialize. OS/library internal allocations, WebView strings and IPC buffers do not have proven erasure.

OS secret stores protect credentials according to the current user's OS/store configuration. This is not protection against a compromised user session, malicious same-user process, unlocked-system access, OS backup/roaming policy or compromised application code. It does not encrypt the Rangoon SQLite workspace, prove tamper resistance, or establish security certification. Linux Secret Service implementations determine their own persistence/encryption behavior; the app does not attest that configuration.

## Isolated entry and native consent

The main workbench has only inspect, open-editor and remove commands. A native-created `cloud-credential-entry` WebView has only read-edit-metadata, submit-new-secret and cancel commands, with both capability and native window-label enforcement. Its path is fixed and navigation is restricted to that exact bundled page. The enforced native CSP remains `default-src 'none'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' asset: http://asset.localhost; font-src 'self'; connect-src ipc: http://ipc.localhost; base-uri 'none'; form-action 'none'; frame-src 'none'; object-src 'none'`. Remote fetch, WebSocket, beacon, forms, frames and subresources are denied by that policy, not merely by the absence of a network command. Asset scope remains empty. Source tests pin those restrictions; rendered negative network-attempt evidence is a separate runtime check. No opener, event, workspace, generic window, network, clipboard-reading or key-readback command is granted.

The entry WebView contains a blank password field; it never receives the existing secret. It temporarily holds newly typed text and sends it once through bounded raw IPC. This is a deliberate, documented refinement of native custody: the main renderer never sees the key, but the isolated entry renderer necessarily sees what the operator types. Clear the input and temporary byte buffer on submission/cancel; no reveal control, browser persistence, autocomplete, logs, URL serialization or saved draft. This reduces exposure; it does not promise JavaScript-memory erasure or trusted input against OS/application compromise.

The explicit open-editor action first reads and validates the app-owned slot natively, retaining its exact envelope or absence as the expected state. An unavailable/corrupt slot fails before opening the editor. The main command retains a random, single-use edit ID and waits for the isolated entry. Submitted material cannot choose the provider. Native code displays a final parented OS Save/Cancel question naming OpenAI and the create/replace effect. No renderer approval boolean is accepted. A mutex serializes the native phases `reading -> editing -> submitted -> prompting -> storage -> final` (inspection ends after reading; removal skips editing/submitted). A close/cancel before the atomic transition into `storage` marks the operation cancelled and prevents that transition, including cancellation while the OS question is visible. Once the storage transition wins, cancellation cannot claim to undo the operation. Old IDs, duplicate submissions and late affirmative callbacks cannot revive a cancelled operation. The blocking worker owns its lease and dialog parent through confirmation and storage even if its IPC waiter disappears. Prevent destruction of the parent while the question or blocking OS operation is active. Once an OS mutation starts, do not report cancellation or promise rollback; wait for a verified result or an uncertain result.

Removal first reads the app-owned slot, asks a parented OS Remove/Cancel question, and rereads the exact envelope immediately before deletion. A changed credential refuses deletion. OS storage does not offer compare-and-swap: another same-user process can still race after the reread, outside this boundary's protection. Missing credentials are reported missing, never as a newly successful deletion.

## State, response and failure contract

Main commands return a fixed platform `backend` and `schemaVersion: rangoon.cloud-custody.v1`, `provider: openai`, `authority: none` and a closed outcome. Successful inspection/save returns `revision` as 64 lowercase hex characters. Outcomes: `stored`, `missing`, `saved`, `removed`, `cancelled`, `failed`. Closed failure codes: `invalid_request`, `busy`, `unavailable`, `invalid_stored_credential`, `changed`, `write_uncertain`, `confirmation_unavailable`. No backend error string or submitted content crosses IPC. An explicit subsequent inspection is required after uncertain writes; never automatically retry or claim the old key remains intact.

An inspection succeeds only after validating the envelope. Immediately before save, reread the slot and compare its full envelope/absence with the native expected state captured at editor open. Refuse with `changed` if it differs; this detects changes during entry/confirmation, while retaining the same documented non-atomic OS compare/write race as removal. A save succeeds only after writing then reading back byte-identical envelope content in the same blocking worker. Removal succeeds only after delete then a confirmed missing read. Any failed write/delete or unverifiable post-write state is `write_uncertain`; no local success claim follows. All store access is serial within the application process. A panic while mutation may have occurred also yields `write_uncertain`.

The editor metadata is a separate `rangoon.cloud-credential-edit.v1` DTO containing fixed provider and the current random edit ID. Submit/cancel requests require that exact ID and a closed schema. Submit requires raw `InvokeBody` bytes, capped at 12,544 bytes before native JSON parsing (enough for six-byte JSON escapes of 2,048 ASCII bytes plus metadata). Cancel is capped at 256 bytes. Tauri/WebView transport buffers may already be allocated before these handler limits; this is not a pre-dispatch memory bound. Read/inspect/open/remove commands accept only an empty body. Submit/cancel return only `{accepted: bool}`, and unavailable editor metadata is null. Reject oversize before native parsing; reject duplicate/unknown fields, malformed UTF-8, invalid handles and replay. One submission consumes the editor. No secret appears in the main command result.

## Validation and qualification

Required source checks: strict input boundaries, distinct window capability lists and native label rejection, single-use/stale IDs, serialization without secret leakage, store-unavailable/missing/corrupt/changed states, cancellation before write, save/remove verification, ambiguous mutation failures, busy/close behavior, no global/default/mock production store and no provider traffic. Unit tests use injected in-memory stores, never OS credentials. Ordinary test/build startup must not touch OS stores.

OS smoke tests require explicit opt-in, a fresh random QA-only service identifier, synthetic credentials and cleanup of only that owned test entry. Never inspect or use existing user keys during development. macOS smoke proves only that tested configuration; Windows/Linux runtime custody and GUI, full keyboard/screen-reader behavior, packaging/signing and cloud transport remain separate qualification gates. Three-OS builds alone do not establish secure runtime custody.
