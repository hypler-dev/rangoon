# Encrypted workspace backend and native adoption

Authority: the accepted local-first V1 objective and Jeff's October 7 request to address database encryption in [intent.md](intent.md). This specification refines storage confidentiality without changing domain identities, authority semantics or the accepted three-desktop release target. Current evidence and acceptance belong only in [development.md](development.md).

## Current boundary and delivery sequence

The current native application uses plaintext SQLite and plaintext portable backups. OS custody implemented for OpenAI credentials does not protect workspace data. Unkeyed content hashes establish consistency, not authenticated history. Encrypting storage does not authenticate a local review, prevent replay of an entire older valid database, or protect an unlocked compromised process.

Deliver encryption through four bounded stages:

1. **E1a keyed portable store:** explicit caller-supplied 32-byte key, optional pinned SQLCipher backend, existing validated store/schema APIs, and synthetic encrypted create/reopen, rejection and integrity tests. No native key lookup, schema migration or user workspace mutation.
2. **E1b native custody and new encrypted workspace:** separate OS-protected database key slot, native-only generation/use, explicit locked/missing/unavailable/recovery states, exact identity pairing and an encrypted-only new-workspace path. Never reuse an API credential. No renderer key, ambient secret lookup, environment-variable key or plaintext fallback. Decide unlock/recovery UX before enabling the native backend.
3. **E1c verified legacy migration and recovery:** explicit conversion into a separately created encrypted destination, validate all existing records/identities and reopen with the retained key before cutover; preserve the original until an explicit retention decision. Journal an interruption-safe migration/cutover state without exposing keys. Key-loss recovery, concurrent writers, disk exhaustion, rollback and rotation require their own exact contract and tests. Never silently replace unreadable data with an empty store.
4. **E1d encrypted recovery archives:** separate authenticated versioned archive format and explicit portable recovery-key/passphrase custody. OS-bound workspace keys alone cannot supply cross-device recovery. Existing plaintext archives and target instruction files remain explicitly disclosed legacy formats; do not relabel their digests as encryption/authentication.

E1a, E1b-1 and E1b-2a source acceptance are recorded in the ledger. E1b-2b now stages native admission/drain, managed command routing, retained-data cleanup and consent mounting. E1b-2 must supply explicit consent, complete session/operation custody, identity/path persistence and the unlock/create/lock UI before native adoption. Migration, rotation and encrypted backups remain later work; these source packets must not change current desktop storage or imply the application is now encrypted. Model retained inspection remains next local workflow; durable model derivations follow the storage/recovery decision.

## Installation, first-run setup and management surfaces

Authority: Jeff's October 8 direction in [intent.md](intent.md#encrypted-installation-and-management-direction--october-8-2026). The accepted outcome is an encrypted local database set up as part of installation/onboarding, accessible through Simple, Advanced and eventual CLI management. This section is the single behavior authority for that direction; implementation evidence remains in [development.md](development.md). Detailed behavior below is a proposed adoption contract, not a claim that installers, encrypted desktop routing or workspace CLI commands exist.

### Installation and first-run flow

Separate installing signed/qualified application binaries from provisioning user-owned data. Run database setup in the first interactive launch under the intended OS user, not in an elevated installer, package-manager post-install hook or shared system account. Installation may offer “Launch Rangoon and set up workspace”; it must not generate a key before that user reviews the action. Reinstallation and upgrades preserve existing data and keys and inspect compatibility before opening them. Uninstall removes binaries by default; removal of workspace data or OS key slots requires a separate reviewed destructive-action contract. No automatic migration, key regeneration, directory scanning, provider connection or telemetry upload is part of setup.

Proposed onboarding sequence:

1. **Welcome:** Rangoon branding, Simple as the default presentation, local-first explanation, and one primary action: “Set up encrypted workspace.” No account, model or LNSAT is required. “Continue without saving” permits in-memory instruction analysis; it never creates a plaintext database. Advanced is reachable without changing this security boundary.
2. **Check local requirements:** inspect the qualified cipher build, app-local root, cooperating-owner lock, known binding state and ability to open the OS key service. Opening the service does not read a workspace key or grant consent to create one. Show unavailable, incompatible, busy or recovery-needed states honestly. No progress percentage unless measured. Determine explicit absence versus unreadable state; an error is never evidence that the workspace is empty.
3. **Review setup:** show the application-owned storage location, local encrypted-at-rest scope, OS-account key custody, size limits, lock behavior and recovery availability. Show that ordinary instruction exports are plaintext and external calls need separate consent. A short readable summary precedes technical details. If portable recovery is unavailable, explain that loss of the OS key can make the database unrecoverable; do not imply that copying the database alone is a backup with recoverable keys.
4. **Confirm creation:** native-owned confirmation is bound to the exact prepared workspace identity, mode and operation generation. Consume the confirmation attempt once. Recheck custody, create an exclusive destination and provisioning record, generate a separate random database key, write it to the exact OS slot and require exact readback. Create and authenticate an empty encrypted database, validate its complete inventory, then durably mark ready before showing success. Errors after a write attempt produce a recovery state, not an automatic retry or a new empty database.
5. **Open workbench:** show a real empty inventory and a primary “Import instruction file” action. Maintain the original grouped navigation, compact banner, central work area and inspector. No fabricated starter source, skills, approvals or fleet counts. Lock controls and encryption status stay visible. Persist only nonsecret presentation preferences; never key bytes or unlock credentials in renderer storage.
6. **Subsequent launch:** inspect the known binding without automatically reading a database key. Start locked and offer “Unlock workspace.” Explicit unlock opens the identity-bound OS slot and authenticates the database before returning content. An OS vault already being unlocked does not by itself constitute Rangoon unlock consent.

The current Owner source cannot implement step 4 unchanged: `prepare_create` retains a validated selected AnalysisReport, and creation calls `save_v1` with it. Empty initialization requires a separately frozen store/Owner packet preserving the existing selected-source creation path and identities. Do not fabricate an empty instruction file, pass a synthetic report, or redefine a saved-source record to obtain onboarding. Proposed setup metadata is nonsecret and versioned; no new schema or metadata format is frozen here.

A future explicit “Import file and set up workspace” shortcut may reuse the existing retained-source path after showing both storage consent and the exact selected file. It must preserve standalone empty setup and not hide persistence behind source selection.

### States and recovery behavior

These are proposed user-facing states mapped to closed host diagnostics, not a replacement for existing enums. Presentation mode never changes state transitions.

| State | Simple experience | Advanced/CLI detail and permitted next action |
| --- | --- | --- |
| Not set up | Set up encrypted workspace; analyze without saving | Nonsecret backend/known-root inspection; prepare creation only after explicit selection |
| Provisioning | Setting up; prevent duplicate requests | One consumed confirmation and exclusive Owner; durable progress inspection must not expose keys |
| Locked | Unlock; no saved content visible | Nonsecret identity/build/state metadata only; explicit unlock required before inventory or content checks |
| Unlocking | Waiting for local key service/authentication | Keep new data operations closed; cancellation must await retained callback custody |
| Unlocked | Import/edit/save, encryption status, Lock | Existing typed content services; exact identity/key revalidation on every operation |
| Locking | Closing workspace; operations unavailable | Close admission, invalidate generation, cancel cooperatively, await all callbacks, purge native/renderer content, then drop keys/handles; no early “Locked” label |
| Busy | Workspace in use; explain safe retry | Owner contention never steals a file lock or opens a second direct handle |
| Unavailable | Explain unavailable cipher/key service or unsupported build | No plaintext fallback, ambient secret lookup or insecure key file; in-memory analysis may remain available |
| Legacy plaintext detected | Clearly label existing unencrypted data; offer planned migration information | Encrypted creation never adopts it. E1c must preview and verify an explicit separate-destination migration; never claim the old copy is encrypted |
| Recovery required / invalid data | Preserve data; stop writes; provide diagnostic guidance | No automatic key replacement, cleanup, restart-to-retry or database reset. Durable E1c recovery must reconcile actual provisioning/commit evidence before any repair |

Default lock-policy proposal: explicit unlock on launch; a 15-minute idle timeout; and lock requests on host-session lock or suspend where platform events are qualified. Exact idle activity, OS events, multi-window behavior and callback drain are implementation decisions requiring their own contract. Changing a timeout requires a deliberate settings save; disabling automatic lock is excluded from the initial slice. Locking may wait for an in-flight OS prompt or committed write; a timeout must not falsely claim key release. App lock purges application references and visible content, not screenshots, swap, crash dumps, allocator remnants, exported files or memory of a compromised process.

Current sticky recovery is Owner-local memory plus persisted provisioning/binding evidence; it is not a durable journal for all uncertain writes. A restart is not recovery acceptance. Release-grade setup must reconcile interrupted provisioning and ready-state write uncertainty under a separately specified durable protocol, with process-kill/disk-full tests and no automatic repair. This section does not silently extend the existing ready-binding format or convert any past fixture into crash-recovery proof.

Switching mode changes visible controls only; it never creates a database, unlocks it, uploads content, grants authority or lowers validation. Basic safety, clear failures, lock/unlock and data-loss warnings remain available in the free Simple experience. CLI complexity likewise grants no extra approval or execution authority.

### Proposed CLI transport and commands

Reuse the same typed Owner services and immutable domain contracts. Do not expose a generic store handle, arbitrary SQL, key export, `--key`, environment-variable keys, secrets in arguments or direct SQLite file access. Do not read ambient provider credentials. Operating-system secret service is the only planned local database-key custody route in this phase; passphrase/archive key custody belongs to E1d.

The first CLI architecture proposal is a bounded standalone native host for a selected known workspace, holding its cooperating-owner lock for the entire command or explicit interactive session. It shares implementation with desktop services, not a second database stack. Desktop ownership causes a clear busy refusal; a separate `rangoon workspace lock` process cannot revoke another process's Owner. No broker, background daemon, socket or remote administration channel is added implicitly. A future authenticated local broker would require a distinct peer-identity, endpoint-permission, consent and lifetime contract; it is not required for initial headless inspection.

Proposed command families, **not current executable syntax**:

```text
rangoon workspace status --json
rangoon workspace doctor --json
rangoon workspace setup
rangoon workspace session
# Within an explicit native session: unlock, inventory, verify, lock, exit
rangoon workspace backup inspect
rangoon workspace restore preview
rangoon workspace data delete preview
```

`status`/`doctor` default to nonsecret build, known-binding and availability checks. They never unlock or claim database integrity from file presence. Inventory and integrity checks require explicit native unlock in the same owning session. Each mutating command must preview exact scope and obtain a one-attempt confirmation bound to workspace identity, current state and host generation. Noninteractive mutation is closed in the first CLI slice; no blanket `--yes`, unsafe override or reusable unlock token. A later automation contract may enable explicitly scoped plan application without exposing keys, but command design here is not approval for it. Content output, support bundles and plaintext instruction export each require explicit output selection and disclosure; JSON errors never echo rejected source, keys, paths or OS diagnostics. Redact user locations from support output by default.

CLI sessions lock and release custody on exit; abnormal exit relies on OS resource release, not a secure-erasure claim. CLI and desktop must produce equivalent domain receipts, provenance, closed errors and state/refusal behavior for supported operations. Existing source limits and store bounds remain unchanged. Missing provider integrations never block local encrypted setup or core content work.

### Management decisions and security limits

The pinned SQLCipher backend supplies encrypted pages and page authentication; see its [security design](https://www.zetetic.net/sqlcipher/design/). Rangoon retains the E1a checks, memory-only temporary store, restricted app-local file handling and no plaintext fallback. Those mechanisms do not establish whole-store freshness, authenticated human review, government compliance or protection from an unlocked compromised host. Cipher/version/OS custody compatibility remains qualified per packaged target, not inferred from dependencies.

Release planning must cover encrypted database, journals and temporary files; key custody; nonsecret metadata leakage; logs and crash reports; backups; exports; upgrades; uninstall; concurrency; and suspended/locked sessions. Database encryption does not encrypt current JSON backups or exported instruction bundles. Until E1d is qualified, the proposed new encrypted setup flow must not offer current plaintext backup as its default recovery action; any explicitly retained advanced legacy export must disclose plaintext and require its own exact consent. Do not claim portable recovery exists. Dependency-aware logical deletion cannot promise physical erasure from SSDs, snapshots, backups or exported files. Future key rotation/migration must verify the replacement before cutover and preserve rollback evidence; destructive key deletion requires a separate contract and must never be used to hide an uncertain write.

## E1a backend and public API

Keep `rusqlite =0.40.2` and its currently locked `libsqlite3-sys =0.38.2`. Its cached Community SQLCipher amalgamation identifies version `4.14.0`. Add only optional `rangoon-store` feature `encrypted-sqlite`, enabling `rusqlite/bundled-sqlcipher`, and exact existing dependency `zeroize =1.9.0`. No SQLCipher CLI, commercial package, provider or account is installed. No vendored-OpenSSL feature or dependency upgrade is included. The upstream build selects CommonCrypto on Apple or an available OpenSSL crypto provider; Windows/Linux build and runtime qualification remain open. Runtime `cipher_version` must report exactly `4.14.0 community` (the pinned source emits its edition suffix) before an encrypted handle is accepted; reject crypto-provider labels other than `openssl` or `commoncrypto`, recording the actual tested provider/version in the ledger; this is backend identity, not certification.

Expose non-Debug, non-Serialize `WorkspaceKey::from_bytes([u8;32])`, with zeroizing ownership; entropy and native key custody belong to the trusted caller until E1b. Do not claim arbitrary caller bytes are random. Share key ownership through `Arc` when cloning a workspace; zeroize the owned bytes on final drop, without claiming erasure of caller copies, SQLite/parser/OS allocations or process memory.

`Workspace::encrypted(directory, key) -> Result<Workspace, StoreError>` is explicit. Both the key type and constructor remain callable in default builds. The constructor rejects unsupported builds or an unexpected cipher profile before filesystem access. Existing `Workspace::new(directory)` remains the explicitly plaintext legacy constructor. An encrypted request never falls back to it. Constructor verification uses only an in-memory connection; reads/listing of a missing workspace must still create no directory/file. No key or caller path appears in diagnostics or serialized records.

Every encrypted file connection must set the raw key before reading schema or data, verify the pinned cipher version and require its unchanged default SQLCipher-4 profile, then verify `cipher_page_size=4096`, `cipher_use_hmac=1`, `cipher_plaintext_header_size=0`, `kdf_iter=256000`, `cipher_hmac_algorithm=HMAC_SHA512` and `cipher_kdf_algorithm=PBKDF2_HMAC_SHA512`. Raw random key bytes bypass passphrase derivation; the KDF setting remains part of the fixed compatibility profile, not a password-hardening claim. Force `temp_store=MEMORY` and verify its value is 2. Reject a nonempty file whose size is not a multiple of the fixed 4096-byte encrypted page size. Before any schema/record read or write, run `cipher_integrity_check` over the main database and accept only zero result rows; every result row or query failure maps to `encrypted_store_invalid` without exposing its text. Do not run the file-only check on the constructor's in-memory version probe. Only a zero-length file created exclusively by the current encrypted write may initialize. An existing zero-length file is rejected, including after truncation or an interrupted initial creation; it is never silently reinitialized. A new zero-length explicitly created file has no stored pages to authenticate; verify readable empty schema before initialization. Then validate readable schema before existing store operations. Preserve `trusted_schema=OFF`, `synchronous=FULL`, rollback journal `DELETE`, current bounds, locks, no-follow/path checks, schema/record validation and immutable identities. Do not weaken the existing read-only connection rules. Disallow nonempty plaintext databases through the encrypted constructor: conversion requires E1c; setting a key is not plaintext migration.

Closed new public diagnostics: `encryption_unavailable` for unsupported/unqualified backend; `encrypted_store_invalid` for unreadable keyed schema or rejected keyed content. Do not diagnose a wrong key versus tampering/corruption as distinguishable from one failed authentication/read. Both return no saved content. The main-file authentication pass costs up to a 64 MiB scan per encrypted connection; measure this before native adoption, with no performance guarantee from this packet. It does not prevent modification after the check or establish whole-file freshness. Later failures retain existing closed store diagnostics. Plaintext reopening of ciphertext must fail through existing validation and leave original bytes intact.

The key parameter is trusted host input, not renderer JSON, command arguments or a loggable configuration field. Implement the existing safe `rusqlite` pragma API; avoid new unsafe FFI and keep `#![forbid(unsafe_code)]`. Raw-key SQL/parser copies may exist transiently and must remain outside any erasure claim. Disable SQLCipher logging before keying; no tracing/profile/logging of key statements is permitted. Do not rewrite process-global cipher defaults or attempt to repair a conflicting profile.

SQLCipher's documented [keying and verification APIs](https://www.zetetic.net/sqlcipher/sqlcipher-api/) require keying before first schema/data use and an actual schema read to verify it. Its [security design](https://www.zetetic.net/sqlcipher/design/) describes page authentication and encrypted journal storage. These are upstream mechanisms to test in our pinned build, not evidence of Rangoon certification. Page authentication does not prevent valid-page or whole-store rollback; hashes and encrypted storage never grant execution authority.

## E1b-1 native key-custody primitives

This source-only substage prepares actual native key creation, OS-slot access and exact retained-key revalidation without registering commands, enabling encrypted storage by default or touching an existing user vault/database. The desktop crate gains a small Rust library with `workspace_keys`; it is not a renderer API or an unlock UI. An optional desktop feature `encrypted-workspace` enables the existing store cipher feature. Default builds reject every encrypted-key custody/access operation before vault, entropy or filesystem access. The later nonsecret workbench admission gate preserves ordinary plaintext operation in default builds. `WorkspaceId::generate` is a separate explicit native identity utility; it does not access the vault.

### Identity, namespace and secret ownership

`WorkspaceId` is exactly 32 bytes, generated through pinned `getrandom =0.3.4`, with strict 64-character lowercase hexadecimal parsing for a future trusted host manifest. Reject an all-zero identity and malformed, uppercase, shorter or longer representations. It is a nonsecret random identity, not a source digest, key fingerprint, path or provider identity. Renderer strings never select an OS slot in this packet. The production caller supplies an application identifier of 1–128 ASCII alphanumeric, dot or hyphen characters. `OsSlot::open(identifier, id)` derives service `<identifier>.encrypted-workspace-key.v1` and account `workspace-<64 lowercase hex>` using existing pinned macOS Keychain, Windows Credential Manager and Linux Secret Service dependencies. This is distinct from the OpenAI credential namespace and accounts; no fallback or default-store mutation is permitted. Native open checks the cipher backend before opening an OS store. Locked or unavailable OS service errors remain `unavailable`; only the backend's explicit NoEntry means a missing key.

The exact 121-byte binary envelope is ASCII `rangoon.workspace-key.v1` followed by NUL, then workspace identity (32 bytes), independent random record revision (32 bytes), and raw database key (32 bytes). Require exact header/length/identity and nonzero identity, revision and key, with no ignored trailing bytes. The public retained key has no Debug, Serialize, Clone or raw-key getter. It owns a zeroizing envelope. Decode returns no payload in errors. Keys/revisions use explicit OS entropy, never environment variables, passphrases, API credentials, imported source, logs or model output. Partial entropy failure returns `entropy_unavailable` and owns temporary buffers through zeroizing wrappers. This is best-effort zeroization of owned buffers, not all allocator, OS, parser, caller or SQLite copies. The revision is not derived from the key.

### Frozen Rust surface and behavior

Public surface: `WorkspaceId::{generate,parse,as_hex}`, `Store::{identity,read,write}`, `OsSlot::open`, `create_key`, `read_key` and `verified_workspace`. `Store::read` returns `Result<Option<Zeroizing<Vec<u8>>>, Error>`; write accepts a borrowed byte slice. `RetainedKey` is opaque. Closed snake-case errors are `invalid_request`, `backend_unavailable`, `entropy_unavailable`, `unavailable`, `missing`, `already_exists`, `invalid_stored_key`, `changed`, and `write_uncertain`. They carry no path, key, native provider diagnostic or payload.

Exact signatures and ownership:

```rust
pub trait Store {
    fn identity(&self) -> &WorkspaceId;
    fn read(&self) -> Result<Option<zeroize::Zeroizing<Vec<u8>>>, Error>;
    fn write(&self, envelope: &[u8]) -> Result<(), Error>;
}
impl WorkspaceId {
    pub fn generate() -> Result<Self, Error>;
    pub fn parse(value: &str) -> Result<Self, Error>;
    pub fn as_hex(&self) -> String;
}
impl OsSlot {
    pub fn open(application_identifier: &str, identity: WorkspaceId) -> Result<Self, Error>;
}
pub fn create_key(store: &impl Store) -> Result<RetainedKey, Error>;
pub fn read_key(store: &impl Store) -> Result<RetainedKey, Error>;
pub fn verified_workspace(
    store: &impl Store,
    retained: &RetainedKey,
    host_directory: std::path::PathBuf,
) -> Result<rangoon_store::Workspace, Error>;
```

`WorkspaceId` is an opaque immutable value with Clone/PartialEq/Eq for host binding; it has no public mutable bytes. `OsSlot::open` consumes its identity, and callers clone only the nonsecret ID when needed. `RetainedKey` owns its envelope and is borrowed by verification; every successful workspace construction gets its own zeroizing key owner through the existing store API. All `Workspace::encrypted` constructor errors map to `backend_unavailable`; later actual store-operation errors remain existing StoreError values, outside this primitive's return type. Before a write attempt, native/fake slot read errors map to `unavailable`; after a write attempt, every failure maps to `write_uncertain`. Entropy errors map to `entropy_unavailable`. No underlying error value is formatted or serialized. The shared private `Entropy` seam also supports `generate_identity_with_entropy(&impl Entropy) -> Result<WorkspaceId, Error>`; source tests prove identity entropy failure independently. OS APIs may allocate a retrieved value before exact-length validation; this packet does not claim a pre-allocation OS read bound.

`create_key(store)` first verifies the optional cipher backend using an in-memory dummy key/profile probe. Read the selected identity-bound slot once. Any existing value, including malformed content, returns `already_exists` without entropy generation or writes; it is never replaced or deleted. An unreadable slot returns `unavailable`. Only an observed absent slot permits generation of independent random revision/key bytes. After a write attempt, re-read and require complete byte equality with the retained generated envelope. Any write failure, read failure, missing or different returned value is `write_uncertain`, even when bytes may have reached storage. Do not retry, clean up, delete or silently report saved. No database is created by provisioning a key.

`read_key(store)` first verifies the backend, then reads once, requires explicit presence and strictly decodes against `store.identity()`. Missing or invalid keys are not regenerated. `verified_workspace(store, retained, host_directory)` verifies backend and exact identity before vault access, re-reads the full envelope and rejects changed/missing/invalid content or read errors. Missing, malformed or different re-read values return `changed`; a read failure returns `unavailable`. Only identical retained and current bytes may produce the existing `Workspace::encrypted` handle. This constructor does not read or authenticate an actual database. Its later store operations perform E1a checks, so returning this handle must not be described as an unlocked/authenticated workspace. There is no plaintext constructor or migration call on this path. A key-only operation creates no filesystem state.

OS stores do not provide compare-and-set through this API. Read-before-write and verification are not a cross-process lock or atomic absence guarantee.
