## E1c provisioning recovery and outcome reconciliation

This continues the [accepted encryption program](intent.md#provisioning-recovery-continuation--october-15-2026). The baseline investigation below is historical; the E1c-1 subsection freezes the implemented source protocol, with validation and qualification limits in the canonical ledger. No new cipher or database schema is needed to investigate this boundary.

### Verified problem and required outcome

At baseline `b8d21e6`, Owner recovery was process-local. Existing native fixtures deliberately show that setup faults before Ready synchronization/readback can return WriteUncertain while leaving a Ready binding; a newly acquired Owner can then prepare unlock. The post-save fixture likewise preserves real committed bytes but loses its recovery flag on reacquisition. Explicit unlock already requires confirmation and authenticates the store; it must not be described as an automatic open or proof that the previous operation was acknowledged. The E1c-1 fixtures strengthen this baseline by requiring durable Pending and explicit reconciliation; neither fixture set is a production crash-durability guarantee.

The target is usable restart recovery with no implicit retry, replacement key, replacement database, source repair or execution authority. Preserve ordinary successful setup, clean lock and explicit restart/unlock. A verified committed operation and delivery of its result are different facts. After an interrupted or uncertain operation, expose available recorded evidence and require qualified explicit reconciliation before resuming affected mutations. Content inspection and reconciliation do not establish an execution approval.

### Failure matrix for the next source packet

| Observation | Required behavior | Evidence needed before normal work |
| --- | --- | --- |
| No operation intent, binding or managed artifacts, with explicit readable absence | Allow preparation only; no vault/database writes | Exact absent-state and directory custody checks |
| Known orphaned managed artifacts, absent binding, or contradictory records | RecoveryRequired; never treat the root as a new empty workspace | Explicit inspection of the known app-owned root; no automatic adoption/deletion |

| Ready binding after setup returned an uncertain result | Do not infer that the caller saw success; retain the previous attempt for inspection | Consistent durable intent/result evidence and separately confirmed reconciliation |
| Valid recorded commit but missing delivery acknowledgment | Present committed and unconfirmed delivery as separate facts; do not automatically repeat the operation | Read-only exact revision/inventory comparison and explicit next action |
| Malformed, unreadable, linked/replaced or identity-mismatched recovery evidence | Closed recovery/unavailable state; no key regeneration or fallback | Bounded no-follow/same-file inspection; no implicit repair |
| Successful clean close and consistent completed records | Locked; offer ordinary explicit unlock | Qualified identity/key/store checks before returning content |
| Final record write/sync/readback or cleanup result is unknown | Remain conservative in the current process; do not claim that a later process can infer the failed response from readable bytes alone | Protocol-specific crash and filesystem-failure evidence; explicit reconciliation when observation is ambiguous |

### Protocol constraints and rejected shortcuts

An operation marker can be a useful write-ahead fence, but deleting the only marker and then failing directory synchronization can leave Ready plus an absent marker. That observation cannot prove clean completion. A completion receipt written before Ready also does not fix the current BeforeReadySync/BeforeReadyReadback gap. Moving the last Complete write after Ready merely moves the final uncertain-write boundary: a failed call can still have persisted readable bytes. No local-file scheme may claim perfect knowledge of a caller's result after arbitrary storage failure.

A permanent Pending marker that is never cleared safely refuses later opens, including successful normal restarts. That is a conservative test substrate, not an accepted replacement for usable lock/restart/unlock. Do not implement that regression as a completed recovery feature. The next mechanism must separate durable operation evidence, actual database state, result delivery and the explicitly confirmed reconciliation decision. It must retain enough information to inspect uncertainty without inventing a failure/success fact or replaying the mutation.

Recovery records must contain only bounded versioned nonsecret metadata, exact workspace/attempt identities and finite state. No source content, database key, provider credential, key fingerprint or renderer-selected path is permitted. Unknown fields/states and unavailable reads cannot become absence. No-follow/reparse rejection, same-file/directory custody, exclusive creation, OS-appropriate durability and cross-process ownership must be qualified together. Unkeyed metadata is not authenticated tamper or rollback protection; OS-account compromise, deliberate deletion and arbitrary filesystem/hardware failure remain separate limits. The current native same-file helper returns true on non-Unix targets, and directory synchronization is also Unix-only; native restart durability cannot be inferred from portable source or default hosted build checks.

### Durable operation protocol E1c-1

The October 15 completion continuation opens this source implementation. Use two private fixed-size slots, `encrypted-workspace.operation.pending` and `encrypted-workspace.operation.terminal`, never a deleted sole marker. Pending is written only to its slot and Observed/Reconciled only to the terminal slot. Keep the canonical Pending intact throughout every terminal write. A coherent same-sequence/same-attempt pair selects terminal; a Pending exactly one sequence newer than terminal selects Pending. The next Pending may replace the old Pending only after a valid terminal resolved that old attempt. No unbounded audit log or historical retention guarantee is added. Its versioned binary encoding contains only a finite operation kind (source/empty setup, source save, capability create/revise/review, workflow save, composition, restore, deletion), Pending/Observed/Reconciled phase, nonzero monotonically increasing u64 sequence, native-generated workspace and attempt identities, and a bounded complete-state ID only for terminal observations. Unknown bytes, invalid padding, overflow, linked files, oversized/short/unreadable records and identity mismatch fail closed. This metadata is neither an authentication seal nor rollback protection. Terminal evidence describes what the host observed; result delivery remains unknown and never authorizes retry.

Persist, synchronize and reread Pending before setup creates its managed directories/key/database or any admitted managed mutation reaches the store. Only a valid resolved terminal (Observed or Reconciled) permits a new Pending; sequence exhaustion refuses. Observed means the native store call succeeded and post-custody/full-inventory verification completed, resolving the storage operation; unconfirmed caller delivery does not require redoing a successful write or manually reconciling every normal write. Preserve Pending on store/post-validation/completion failure and keep the current Owner recovery fence. A terminal record is written only after full store inventory authentication and custody checks; no operation is replayed. A failed final sync/readback can leave readable terminal bytes: a later Owner can report that observation, not infer that the prior caller received success. Ordinary explicit unlock accepts internally consistent terminal evidence and retains existing vault/database authentication. No automatic opening occurs.

Absence is allowed for new setup only when binding, operation record and the known managed parent are explicitly absent. Known orphaned artifacts cannot be adopted as a fresh workspace. Pending blocks ordinary create/unlock before vault access. `inspect_recovery(vault)` is an explicit trusted-host read operation, to be called only after future native consent; it reads the existing key (never creates one), authenticates the complete encrypted database, and returns actual inventory, operation identity and unknown outcome. It retains a private exact binding/operation/directory/key/state observation and a fresh one-attempt token. A matching `confirm_recovery(token, vault)` consumes before work, revalidates every retained observation and exact state ID, then records explicit reconciliation. For valid fully authenticated provisioning, write Ready, synchronize and reread it before writing/synchronizing/rereading Reconciled; keep Pending intact throughout. It performs no user-content/database mutation, key generation, automatic cleanup or retry, and leaves the Owner locked for a separate explicit unlock. Malformed/incomplete setup without an authenticatable database remains closed.

A narrow explicit repair exception refines the earlier malformed-evidence rule: an intact canonical Pending can retain unresolved identity while its bounded regular terminal slot is absent, short or undecodable. An intact terminal with a fixed-size undecodable Pending permits inspection only if the authenticated full inventory exactly equals its retained state ID; confirmation first reconstructs same-attempt Pending, then writes Reconciled. Expose metadata damage and unknown outcome; ordinary unlock always refuses damage. Both invalid slots, unreadable/linked/hardlinked/oversized slots, valid identity mismatch or incoherent sequence remain closed before vault access. A changed authenticated state in the terminal-only damage case refuses repair without metadata or key writes. No implicit repair is allowed.

Repeated interruptions during reconciliation remain inspectable; no new operation may overwrite unresolved evidence. Lock/drop cancels retained recovery plans without erasing durable evidence. Recovery inspection must not implicitly unlock or allow normal reads/writes. Test disposed roots/fake vaults, all mutating families, zero vault access on ordinary Pending refusal, exact no-key-write counters, dropped result/new Owner, terminal faults, stale/forged/replayed tokens, key and state drift, invalid record fuzz/property cases, source byte preservation and clean restart. No new dependencies/cipher/schema. Real process-kill, disk-full, OS-vault/GUI and Windows/Linux durability qualification remain separate; this packet alone does not enable production mounting.

## Closed native-control custody E1c-2a

Native create/unlock/recovery must not temporarily reopen ordinary admission merely to run an OS-key prompt. Existing `Gate::begin` accepts only Open, while current close-cycle and native progress can memoize successful key release. Reopening requires a real lifetime proof for callbacks and retained recovery inspection: cancellation invalidates permission to resume, not actual callback custody. This prerequisite changes only the shared native Gate and independent memory-only tests. The later host supervisor must reset close/release observations before any key access; no such supervisor or renderer is mounted here.

Add opaque non-Clone/non-Debug/non-serializable `ClosedLease`, with only `is_current() -> Result<bool, Error>`. `Gate::begin_closed(&Drain) -> Result<ClosedLease, Error>` accepts only the exact same Gate and current Draining generation with every actual reader/exclusive/model/control owner quiescent; otherwise refuse with existing exact error classes. At most one closed control may exist. Error precedence for both Gate methods is different Gate → Stale; poisoned mutex → Unavailable; Exhausted → Exhausted; non-Draining or generation mismatch → Stale. Then begin_closed alone returns Busy for any actual normal or closed owner; renew_drain deliberately preserves active counts instead of refusing them. ClosedLease::is_current returns Ok(false) for stale/Open/Exhausted and Err(Unavailable) only for poison. Normal Read/Exclusive/Model admission stays closed. The lease belongs to the actual callback and any retained recovery plan, never merely its IPC waiter. State quiescence and `resume` include this custody; dropping the last actual owner releases only the count and never reopens admission.

`Gate::renew_drain(&Drain) -> Result<Drain, Error>` requires the exact current same-Gate Draining token, advances the existing generation and returns a new opaque drain. It does not release or reset any outstanding normal/closed lease count. The old closed lease's current check becomes false immediately, but the new drain stays nonquiescent until its real callback/retained owners drop. Wrong Gate, stale/replayed drain, Open, poison and generation exhaustion fail closed. Repeated cancellation cannot invent a zero count. Existing `request_drain`, `resume`, normal lanes, non-owning witnesses and successful normal lifecycle behavior remain unchanged.

The host supervisor must retain the active drain, serialize final resume against cancellation, and install a new close cycle on renewed drain. An old close ticket/memo cannot complete a new cycle. It must refuse a completed Locked claim throughout any key-acquiring control or retained recovery inspection, discard stale callback results, close Owner/key after actual drain, and retain renderer purge/ack requirements. After a successful explicit create/unlock, drop actual closed-control custody before `Gate::resume`; a racing renewed drain makes the old resume Stale. Resume advances generation again; no old witness, control or prepared plan becomes current. Recovery reconciliation alone never resumes. No renderer-provided token can construct these native capabilities. These are integration obligations, not guarantees supplied by this unmounted primitive.

Acceptance: ordinary lanes remain blocked; exact wrong/stale/Open token errors; single closed control; callback/retained Arc owners outlive a dropped waiter; renewal invalidates current status but preserves actual drain; renewed drain cannot begin another control or resume until prior callback drops; dropping a drain/lease never opens; successful clean resume advances generation; old drains/witnesses remain stale; cross-Gate substitution, repeated renewal, poison and counter exhaustion stay closed. No filesystem, OS prompt, database/key/provider or UI operation is needed. Add privacy compile-fail doctests and run pinned Rust 1.98 native default/encrypted all-target tests, both warnings-denied Clippy variants, privacy doctests, formatting and encrypted build; reference/artifact/whitespace and outside-owned identity proof. Source-only review does not qualify native setup/unlock, real callback integration, OS custody or encryption mounting.

### Transition and delivery invariants

1. A trusted coordinator closes the one shared Gate and invalidates the workspace generation before scheduling cleanup. New data/model/credential work is refused; cancel and profile controls cannot reopen the Gate. Checked generation overflow or poisoned state stays closed.
2. Cancel affected operations and invalidate every pending confirmation. Blocking workers, prompts, transports and claimed mutation plans retain their real leases even when the IPC waiter disappears. Do not hold a coordination mutex across an OS prompt, network operation or blocking file call.
3. Drain callbacks and purge native retained copies. Data-bearing results must be checked against the same workspace identity/generation at completion and native delivery; renderer epochs separately reject a result delivered after purge. Never translate a possibly committed write into "cancelled without change" or silently resend it.
4. Clear renderer state, undo/redo, DOM projections and polling. A cooperative renderer purge acknowledgment supplies UI evidence only; it does not authenticate the renderer or prove secure memory erasure. If cleanup cannot finish, remain closed in a truthful transition/recovery state rather than claiming completion on timeout.
5. Release the opened Owner/key only after callback custody is drained and native cleanup is complete. Keep the binding/file custody and uncertain-write evidence required for recovery. Do not replace a missing key or unreadable store with a new empty workspace.
6. Reopen only after a separately confirmed create/unlock and successful identity/store checks, with a new generation. A dropped Drain, cancelled dialog or old token never reopens admission. E1c must supply durable interrupted-operation fencing before production adoption.

Reference cleanup covers cooperative application owners only; it does not erase exported files, swap, screenshots, crash dumps, parser/allocator remnants or a compromised process. An authorization-provider allow result, local content review, lock completion and actual execution outcome remain different facts.

## Current boundary and delivery sequence

The current native application uses plaintext SQLite and plaintext portable backups. OS custody implemented for OpenAI credentials does not protect workspace data. Unkeyed content hashes establish consistency, not authenticated history. Encrypting storage does not authenticate a local review, prevent replay of an entire older valid database, or protect an unlocked compromised process.

Deliver encryption through four bounded stages:

1. **E1a keyed portable store:** explicit caller-supplied 32-byte key, optional pinned SQLCipher backend, existing validated store/schema APIs, and synthetic encrypted create/reopen, rejection and integrity tests. No native key lookup, schema migration or user workspace mutation.
2. **E1b native custody and new encrypted workspace:** separate OS-protected database key slot, native-only generation/use, explicit locked/missing/unavailable/recovery states, exact identity pairing and an encrypted-only new-workspace path. Never reuse an API credential. No renderer key, ambient secret lookup, environment-variable key or plaintext fallback. Decide unlock/recovery UX before enabling the native backend.
3. **E1c verified legacy migration and recovery:** explicit conversion into a separately created encrypted destination, validate all existing records/identities and reopen with the retained key before cutover; preserve the original until an explicit retention decision. Journal an interruption-safe migration/cutover state without exposing keys. Key-loss recovery, concurrent writers, disk exhaustion, rollback and rotation require their own exact contract and tests. Never silently replace unreadable data with an empty store.
4. **E1d encrypted recovery archives:** separate authenticated versioned archive format and explicit portable recovery-key/passphrase custody. OS-bound workspace keys alone cannot supply cross-device recovery. Existing plaintext archives and target instruction files remain explicitly disclosed legacy formats; do not relabel their digests as encryption/authentication.

E1a, E1b-1 and E1b-2a source acceptance are recorded in the ledger. E1b-2b now stages native admission/drain, managed command routing, retained-data cleanup and consent mounting. Migration, rotation and encrypted backups remain later work; these source packets must not change current desktop storage or imply the application is now encrypted. ### Installation and first-run flow

Separate installing signed/qualified application binaries from provisioning user-owned data. Run database setup in the first interactive launch under the intended OS user, not in an elevated installer, package-manager post-install hook or shared system account. Installation may offer “Launch Rangoon and set up workspace”; it must not generate a key before that user reviews the action. Reinstallation and upgrades preserve existing data and keys and inspect compatibility before opening them. Uninstall removes binaries by default; removal of workspace data or OS key slots requires a separate reviewed destructive-action contract. No automatic migration, key regeneration, directory scanning, provider connection or telemetry upload is part of setup.

Proposed onboarding sequence:

1. **Welcome:** Rangoon branding, Simple as the default presentation, local-first explanation, and one primary action: “Set up encrypted workspace.” No account, model or LNSAT is required. “Continue without saving” permits in-memory instruction analysis; it never creates a plaintext database. Advanced is reachable without changing this security boundary.
2. **Check local requirements:** inspect the qualified cipher build, app-local root, cooperating-owner lock, known binding state and ability to open the OS key service. Opening the service does not read a workspace key or grant consent to create one. Show unavailable, incompatible, busy or recovery-needed states honestly. No progress percentage unless measured. Determine explicit absence versus unreadable state; an error is never evidence that the workspace is empty.
3. **Review setup:** show the application-owned storage location, local encrypted-at-rest scope, OS-account key custody, size limits, lock behavior and recovery availability. Show that ordinary instruction exports are plaintext and external calls need separate consent. A short readable summary precedes technical details. If portable recovery is unavailable, explain that loss of the OS key can make the database unrecoverable; do not imply that copying the database alone is a backup with recoverable keys.
4. **Confirm creation:** native-owned confirmation is bound to the exact prepared workspace identity, mode and operation generation. Consume the confirmation attempt once. Recheck custody, create an exclusive destination and provisioning record, generate a separate random database key, write it to the exact OS slot and require exact readback. Create and authenticate an empty encrypted database, validate its complete inventory, then durably mark ready before showing success. Errors after a write attempt produce a recovery state, not an automatic retry or a new empty database.
5. **Open workbench:** show a real empty inventory and a primary “Import instruction file” action. Maintain the original grouped navigation, compact banner, central work area and inspector. No fabricated starter source, skills, approvals or fleet counts. Lock controls and encryption status stay visible. Persist only nonsecret presentation preferences; never key bytes or unlock credentials in renderer storage.
6. **Subsequent launch:** inspect the known binding without automatically reading a database key. Start locked and offer “Unlock workspace.” Explicit unlock opens the identity-bound OS slot and authenticates the database before returning content. An OS vault already being unlocked does not by itself constitute Rangoon unlock consent.

The original Owner could not implement step 4 unchanged: `prepare_create` retains a validated selected AnalysisReport, and that creation calls `save_v1` with it. The [E1b-2b8 prerequisite](#e1b-2b8-empty-encrypted-provisioning) adds a distinct empty initializer preserving the existing selected-source path and identities.
