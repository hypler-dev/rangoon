## E1d-2 native SQLCipher recovery copy — October 25, 2026

Status: implemented source and selected disposable macOS native recovery evidence recorded under Jeff's explicit request. The [development receipt](development.md#e1d-2-native-encrypted-recovery--october-25-2026) owns validators and independent-review status. Dependency promotion is resolved by reusing the existing pinned SQLCipher backend. The unpublished age experiment is now standalone historical source outside active builds. No compatibility reader/converter is promised for it. No new cipher, KDF, helper process or runtime crypto dependency is introduced.

Recovery profile `rangoon.recovery.sqlcipher.v1` is a raw SQLCipher 4.14.0 encrypted workspace image with the existing 4096-byte/full-header/HMAC profile, Rangoon application ID and supported canonical schema. A separate random 32-byte raw recovery key is stored only after explicit native selection in an owner-only, single-link regular key file: `RANGOON-RECOVERY-KEY-V1` plus LF, 64 lowercase hex characters and LF. File custody checks enforce POSIX owner/mode and link/identity rules; inherited ACLs, shared/network filesystems and other storage media need separate qualification before broad adoption. The selected native proof uses a private local folder. The key file is itself unencrypted: protect it like a password and keep it separately from backups. Anyone holding both files can read the backup; losing the recovery key makes that backup unusable. It is neither a database/provider key export nor a renderer payload. Unknown profiles fail closed; future compatibility needs an explicit qualified reader, not guessed settings.

The trusted host captures an exact complete logical source backup through Owner. A fresh 0700 OS-temp staging directory holds only an encrypted canonical workspace rebuilt with the existing strict empty Restore and a separate recovery key. Retain directory identity/ownership and reject replacement; cleanup only known files. Reopen read-only, verify the existing SQLCipher per-page HMAC/profile/schema/domain checks, exact physical file length equal to page_count × 4096, no sidecars and complete canonical logical archive equality. Counts alone are insufficient. Private staging is not a host-root/same-user-malware confinement guarantee. No plaintext staging file or new logical-backup parser is used.

Native encrypted export rechecks source freshness, exclusively creates a selected `.rangoon-encrypted` file, syncs, rereads that selected ciphertext through another fresh private stage and compares its full logical content before reporting verified success. Source bytes stay unchanged. Wrong keys, malformed images, trailing bytes/pages, sidecars, collisions, source changes, cleanup failure and cancellation/close after a possible write cannot produce a false success. An output/key file may remain after uncertainty; never overwrite it or silently retry. Selected inputs are copied as bounded ciphertext, never opened writable.

Three new workspace-scoped native commands create a recovery key, export an encrypted backup and prepare encrypted Restore. They accept no renderer key/path/content. Existing retained Backup/RestorePlan, generation, expected state and one-shot confirmation still own destination commit. The ordinary restore path preserves every canonical record into a truly empty destination; nonempty destinations retain their existing additive merge and conflict rules. The current registered workspace request header routes all three commands through the existing bridge and Gate. Bad recovery input is a host input failure, not evidence the current destination database is corrupt. Key-loss recovery uses a fresh encrypted destination with a different database key; no key replacement or reset decrypts the original.

Loaded inventory adds advisory `encryptedRecoverySupported` from the actual native backend. Legacy is false; Managed is true only when the encryption/private-key-file implementation is available. Absence or malformed metadata disables modern controls. Native commands recheck support before RNG, pickers or filesystem access. Windows remains unavailable until owner-only key custody is implemented/qualified; Unix source and selected macOS qualification do not assert a Linux GUI pass.

The simple UI offers Back up workspace and Restore backup. Backup explains the separate secret key file, offers Use recovery key or Create recovery key, and retains the dialog after key creation/cancellation. More recovery options contains explicit older plaintext backup import with its warning. Crypto failure never falls back to that path. No secrets enter the workbench, Advanced details, tooltips or logs. Progress reflects actual asynchronous work. Original instruction files and deliberately readable instruction exports remain outside recovery-image confidentiality.

The simple and advanced disclosures distinguish encryption at rest from an unlocked or compromised host, original files and readable instruction exports. Ciphertext integrity establishes neither authorship nor local review, approval or execution authority. No sender authentication, rollback prevention, complete memory erasure, certification or three-OS release claim follows.

Exact source ownership, API/DTOs, lifecycle, negative cases and validators are frozen in the evidence contract `<local-evidence>/rangoon-e1d2-native-recovery-20261025/contract.md`; the development receipt owns results. Root owns store/native paths and reviewers remain read-only. Required proof spans full-history equality, wrong-key/tamper/trailing/sidecar and keyfile custody refusal, cancellation/drain, source preservation, selected-output reread, fresh destination/different key and independent macOS UI/custody evidence. No normal data/key, provider, engine, foreign repository, publication or release gate opens.

### E1d-1 experimental codec profile — October 25, 2026

The following dated source packet refines the E1d-0 candidate below for a synthetic, unmounted experiment only. Jeff's current continuation and [intent record](intent.md#e1d-1-experimental-codec-continuation--october-25-2026) define its exact ownership and validation acquisition scope. Age 0.12.1 is rejected for this experiment after its resolved P-256/HPKE path introduced crypto-bigint 0.5.5 under RUSTSEC-2026-0387; this is a dependency finding, not a proven exploit through the proposed X25519 API. The source pin is `age = "=0.11.5"` with `default-features = false`, plus existing `zeroize = "=1.9.0"`. It avoids that dependency path, but retains beta/testing-only status and unmaintained compile-time dependencies. Native/production promotion remains blocked. Age's 128-bit file key is not an AES-256 or post-quantum claim.

Freeze a private in-memory profile: standard binary age v1 outside; encrypted `RANGOON-RECOVERY-V1` plus LF followed by opaque existing backup bytes inside. `RecoveryIdentity::parse(Zeroizing<String>)` accepts only an explicitly supplied bounded X25519 identity and has redacted Debug, no Serialize or Clone. `RecoveryIdentity::recipient()` returns a public `RecoveryRecipient`; its parser accepts only bounded X25519 public text. `encrypt(&[u8], &RecoveryRecipient)` returns ciphertext; `decrypt(&[u8], &RecoveryIdentity)` returns `RecoveredBackup`, a private zeroizing owner exposing only a borrowed backup slice and redacted Debug. No library key type, public streaming reader, secret reveal, filesystem, process, network, vault or discovery API is exported. Logical archive validation is not performed by this codec; the existing store validator remains required later.

Limits are 68 MiB backup plaintext, 69 MiB ciphertext, 4,096 bytes of header and eight stanza starts before library parsing. Encryption uses one supplied recipient. Decryption uses only the supplied identity; unknown stanzas may be ignored by the format library inside those limits without executing handlers. Successful decryption does not prove that no other recipient exists. Retain all authenticated chunks privately until the final chunk and EOF pass, then check the encrypted inner-version prefix before returning a borrowed body. Unknown versions, wrong identity, tamper, truncation, trailing/concatenated data and size-limit violations never expose partial plaintext. Public errors are fixed `TooLarge`, `Unsupported`, `InvalidOrUnreadable` and `Unavailable`, without raw library messages or source chains. Caller copies and OS/allocator memory are not guaranteed erased.

Use Rust 1.99.1 in a temporary isolated toolchain/cache and credential-free child environment; builds/tests run offline after bounded acquisition. Two-way interoperability uses the independent Go age v1.3.2 reference with disposable data. The committed fixture contains an intentionally public test identity that must never protect real data. Reference release HTTPS/SHA-256 provenance is recorded; no independent signature-verification claim is made. The acceptance matrix below still applies. API/source qualification does not enable native recovery or change existing plaintext instruction export.


### Current source and priority

### E1d-0 design baseline and retained limits

Use an existing specified encryption container rather than design a cipher or KDF. The E1d-0 candidate was the [age v1 format](https://age-encryption.org/v1), wrapping the existing bounded logical backup bytes with an encrypted, versioned Rangoon recovery prefix. Keep the existing backup parser, identities, limits and additive Restore semantics. The format specification and implementation version are different pins. The Rust [age 0.12.1 library documentation](https://docs.rs/age/0.12.1/age/) claims interoperable age files but explicitly calls pre-1.0 releases beta; this is an unresolved dependency-assessment gate, not a production endorsement. No package had been fetched or added at E1d-0. The later E1d-1 assessment and experimental pin above supersede that snapshot; production dependency acceptance still requires exact source/license/advisory, feature/resource and interoperability assessment.

The proposed first profile uses one explicitly supplied X25519 recovery identity/recipient and fresh library-generated encryption randomness. It does not accept SSH identities, plugin handlers, identities discovered on disk, ambient keys or arbitrary recipient collections. Passphrase recovery is deferred until native secret entry and minimum/maximum KDF resource costs have their own measured contract. Future profiles need explicit version negotiation; unsupported profiles fail closed, never silently downgrade. No post-quantum, future-proof, FIPS or certification claim follows from this candidate.

The recovery identity must be independent of the OS-bound workspace database key and provider credentials. A portable backup is not recoverable on another machine merely because the original Keychain slot exists. The first codec takes explicit caller-owned synthetic identity material in tests; it does not touch Keychain, generate a production recovery kit or reveal a secret to the renderer. Later native custody must support deliberate separate recovery-key storage and a restore rehearsal. The user-facing loss statement is explicit: losing both a usable workspace and its recovery identity makes these backups unrecoverable; no replacement key can decrypt them.

Keep plaintext backup content bounded by the current 68 MiB archive ceiling. The codec proposal caps the encrypted input/output at 69 MiB; dependency review must establish that valid maximum payloads fit and attacker-controlled headers cannot cause unbounded allocation or work. Do not introduce compression, recursive archives or arbitrary path extraction. Decryption is not a streaming import: authenticate the complete container, final chunk and EOF before exposing plaintext to the existing backup parser or preparing any mutation. Reject truncation, trailing/concatenated data, oversized input and unsupported profile/version; do not return partial authenticated chunks to a restore caller. Confirm these properties against the selected library API before freezing the source packet.

All plaintext buffers remain in bounded trusted-host memory; do not write a plaintext staging file or return backup contents to the renderer. Minimize copies and use the existing zeroizing-buffer pattern, without claiming secure erasure of every runtime/OS copy. Do not log recovery identities, backup bodies, native paths or raw crypto-library error strings. Use bounded typed outcomes such as unavailable, unsupported, invalid-or-unreadable, cancelled and failed; inability to distinguish a wrong identity from corruption is not a reason to expose internals.

Encrypted-container integrity is not sender authentication or permission to restore. Anyone with the public recipient can construct a new valid encrypted archive. Restoring an older valid archive is also possible. The existing archive validator, native preview, exact destination-state check and explicit confirmation remain required; preserve existing heads and additive history. Never infer an authenticated author, local review, engine approval, execution permission or freshness from successful decryption. Signing and independent rollback detection remain separate, unimplemented capabilities.

## E1c-5 ordinary startup and Legacy adoption — proposed

Status: design proposal under the accepted encryption completion outcome, not source/default-switch or migration acceptance. E1c-4 must finish its full native matrix on one selected executable before ordinary startup is changed. This packet reuses the existing SQLCipher store, Owner, Gate, native consent, durable recovery and close protocol; it does not introduce another encryption architecture. E1d remains the separate encrypted portable-archive/recovery track. The [development receipt](development.md#e1c-5-startup-and-legacy-adoption-design--october-18-2026) owns review evidence.

### Outcome and existing seams

On first launch, a new user explicitly creates an encrypted workspace. An existing user sees the existing data and a reviewable conversion path; the app must not silently substitute a new empty encrypted workspace. A returning encrypted user confirms unlock and receives the same records and identities. Interrupted or ambiguous adoption stays closed with actionable recovery. Source authoring, skills, composition, workflows, compilation and exports remain usable without any provider.

Current `main.rs::source_state` selects Legacy at `app_local_data_dir()/source-workspace`, regardless of the encryption feature. `Workspace::new` is the plaintext constructor; `workspace.sqlite3` is its database name. `SourceAccess::managed_locked`, `workspace_native_bootstrap::present_workbench` and `OsVault` already supply the unmounted encrypted startup/consent seams. `Owner::acquire` owns a different control lock and validates Managed layout; it is not a Legacy migration detector or a lock understood by every old binary. `workspace_source_access.rs::export_backup` already refuses Managed plaintext backup before the picker. Reuse these boundaries rather than adding renderer database selection or a second connection path.

### Reusable transfer and unresolved ownership gaps

Source inspection identifies a preferred transfer base: `workflow_backup.rs::export_workflow_backup` captures validated domain records in one read-only SQLite transaction and returns bounded in-memory archive bytes: schemas 1–3 emit V2, while schema 4 emits V3. `WorkspaceBackup::decode` accepts V1/V2/V3 and rebuilds an in-memory canonical database for validation. Conversion must validate the version appropriate to the captured schema and compare its complete logical inventory, never require a V3 prefix for older valid workspaces. The full schema-4/V3 inventory includes sources, capability histories/reviews, composition recipes/applications/derivations and workflow histories; current schema 1–4 round-trip tests cover logical identity preservation. It is not a physical file image or an encrypted archive. Original imported/exported files, filesystem permissions, journals, Owner/key metadata, durable operation receipts and renderer sessions are outside that logical inventory and need explicit treatment in the adoption record and UX.

Reuse `Owner::prepare_workflow_restore` and `restore_workflow_backup` as the destination mutation seam only against a proven fresh, separately created Managed workspace. Existing restore is an additive union with destination-state checks and durable Restore reconciliation; it does not prove exact source-to-destination equivalence, freeze the source, or commit startup selection. Require a complete destination comparison afterward. Existing limits remain hard refusals, including the 64 MiB logical store, 68 MiB archive and record-count/revision limits; do not expand limits silently to make migration pass. Transfer byte buffers must remain host-owned and bounded, never renderer payloads or plaintext disk archives.

A missing source connection currently exports an empty logical archive. Migration must separately prove the recognized Legacy database exists, is a regular unchanged file and was captured successfully; it must never interpret disappearance or substitution as an intentionally empty source. A valid empty Legacy database is a separate explicit case. No current export plan carries a source-side expected-state token. The new native snapshot custody must bind file identity and captured domain state through preview/confirmation and detect source drift before selection. Managed Restore intent/reconciliation is useful destination evidence but does not bind the Legacy source or supply a durable cutover journal. These are explicit missing mechanisms, not claims that existing backup/restore already performs migration.

### Native startup classification

Inspect only the fixed application-owned storage locations. Do not scan arbitrary directories, use renderer-supplied roots, open vault slots during classification or infer encryption from a file extension. Classification is native, bounded and version-aware; unexpected files, linked/replaced roots, malformed control records and unsupported versions are not an empty workspace. Any discovery result used later must be revalidated under operation custody; a stale preview never authorizes mutation.

### Conversion and restart contract

1. Close ordinary admission and drain actual callbacks before preparing conversion. Capture the source identity and a transactionally consistent view using a reviewed SQLite mechanism; copying only the main database while journals or another writer exist is forbidden. No new plaintext temporary archive is written. Preview exact record counts, schema/limits, destination identity, disk-space estimate and retained-plaintext implications from that captured view.
2. Require native confirmation bound to that source snapshot, destination and plan. Cancel leaves source data untouched and creates no reusable conversion authorization. Source replacement, a changed snapshot or expired plan requires a fresh preview/confirmation. Refuse an unsupported source schema or a dataset that cannot be represented completely; never truncate to fit current caps.
3. Create a separate encrypted destination through existing Owner/key custody. Transfer complete validated domain state and preserve record IDs, revisions, provenance, reviews, composition inputs/results, workflow definitions and relationships. Do not use additive restore as proof that an exact migration succeeded. The version-aware in-memory archive transfer is the preferred existing mechanism; its complete migration inventory oracle and source-custody contract must be frozen before source acceptance; no generic SQL or arbitrary database handle enters the renderer.
4. Verify destination structural/cipher integrity and a deterministic comparison of every migrated domain record and relationship, including compile/export parity for retained definitions. Close the destination, restart a distinct OS process, reacquire the exact Owner and confirm unlock using the retained OS key. Re-read and compare again before selection can be committed. Key lookup failure never regenerates a key.
5. Commit the durable selection only after successful verification. Test every record-write/sync/rename/readback failure boundary and recovery classification. Unknown completion remains a recovery state. Never report success from a UI click, directory existence, content checksum alone or an unobserved background callback.
6. Preserve the original Legacy copy by default. Report that it, its old backups and imported/exported files remain plaintext; encrypting the destination cannot erase those copies. Automatic deletion, secure-erasure claims, key rotation and portable encrypted recovery are excluded. Cleanup needs its own explicit retention/destructive-action scope.

Concurrent/old-version access is a required design decision, not a solved property. A new advisory Owner lock cannot stop an old application that ignores it. A source snapshot preserves a point-in-time dataset; it does not prove no later Legacy writes occurred. Recheck source state before selection and detect later divergence on supported startup; refuse automatic merge or rollback. Before shipping writable cutover, either qualify an exclusive Legacy-writer protocol across the supported upgrade path or explicitly require old processes closed and document the residual inability to prevent an unsupported old binary from reopening retained plaintext. A malicious same-user process or replay of all valid local files remains outside any guarantee supplied by these unkeyed markers.

Do not show an enabled encrypted-backup/restore promise while E1d is unavailable. Explicit target instruction exports remain plaintext with their existing disclosure. An unsupported backend or unavailable OS vault must show a fixed actionable error, not silently choose Legacy.

## E1c-5a startup inspection and existing-source capture — proposed source packet

Status: accepted for the exact unmounted source and disposable tests. Jeff answered “Accepted” on October 19, 2026; [intent](intent.md#e1c-5a-source-acceptance--october-19-2026) records the scope. The heading retains its existing anchor. The completed [selected-artifact native checks](development.md#e1c-4-selected-artifact-native-completion-checks--october-19-2026) remove the earlier native-test wait; their recorded limits remain. This packet implements the first stage of E1c-5, not ordinary startup, conversion or the finished encrypted product. It makes an existing workspace distinguishable from absent, invalid or replaced data before a later adoption operation can select it.

### Fixed paths and observation, not selection

A private native `StartupRoots` derives both roots from the OS application-data anchor: existing `source-workspace` and proposed sibling `managed-workspace`. Keep the current application identifier. Neither root nor any replacement original comes from IPC. Tests inject only disposable anchors; no production caller mounts this module yet. The parent application-data directory is shared with other app state and must not be treated as an otherwise-empty Managed Owner root.

Inspection observes only those two exact roots and bounded immediate entries. It must not create a directory/lock, open SQLite or a credential slot, generate a key, acquire `Owner`, or follow symbolic links/reparse points. `Owner::acquire` can create its lock file, so it cannot be used as a supposedly non-mutating classifier. Existing Owner binding/layout validation remains the later authority for Managed setup/unlock; do not copy its private decoder into a second implementation.

Return finite observations: `FreshCandidate`, `LegacyCandidate`, `ManagedCandidate`, `Mixed`, `RecoveryRequired`, `Unavailable`, or `UnsupportedPlatform`. Candidate means presence and structural observations only. No candidate proves schema compatibility, decryptability, free ownership, consent or saveability. Mixed roots remain closed until a later validated adoption record exists. This packet accepts no adoption-record format. An empty existing Legacy directory, zero-byte database, partial Managed directory, orphan journal, unknown entries or unsupported metadata must never become `FreshCandidate`. A genuinely absent root differs from an inaccessible or replaced root. Valid empty SQLite content is recognized only by the capture validator below.
