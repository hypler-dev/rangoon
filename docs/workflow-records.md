# Workflow records and durable authoring

Authority: the accepted V1 objective and node-building request in [intent.md](intent.md), following [workflow definitions](workflow-definitions.md). This is the controller's W2 implementation contract. Evidence belongs only in [development.md](development.md). It does not authorize engine execution or declare native storage implemented.

## Product outcome and delivery

A workflow has a stable identity and an immutable revision history. Users can explicitly save incomplete typed drafts, reopen them after restart, preserve canvas positions, compare revisions and save a structurally validated definition whose exact local capability references have been resolved. Failure or a stale head preserves the unsaved editor state. No save is an execution approval.

W2a implements portable immutable revision records in `rangoon-workflow::records`. W2b must implement local storage and its complete migration, backup/restore and deletion lifecycle together before exposing a writer. W2c adds native commands, and W3 connects the actual Workflows editor to them. The sample workflow page stays synthetic until replaced. These are stages of the same durable authoring outcome, not substitutes for it.

## W2a portable revision contract

`workflow_id_from_nonce(&[u8; 32]) -> String` returns `workflow:` plus lowercase SHA-256 over `rangoon.workflow-id.v1\0` followed by those exact 32 bytes. The future native creation flow must generate a fresh nonce from OS randomness once per new workflow and retain the resulting ID for retries. This pure function neither supplies nor claims entropy. The nonce is not a credential and does not need to be retained in a record. Identical initial definitions can belong to distinct workflows. A workflow ID is not a W1 definition ID or an authority token.

`prepare_revision(workflow_id: &str, parent_revision_id: Option<&str>, intent: SaveIntent, definition_bytes: &[u8], layout_bytes: &[u8]) -> Result<WorkflowRevision, RecordError>` constructs a candidate immutable record. `decode_revision(bytes: &[u8]) -> Result<WorkflowRevision, RecordError>` strictly decodes and verifies one serialized record. `WorkflowRevision` has private fields, serialization but no Deserialize implementation, read-only getters, and a fallible bounded `serialized_bytes()` method. Its exact getters are `id(&self) -> &str`, `workflow_id(&self) -> &str`, `parent_revision_id(&self) -> Option<&str>`, `intent(&self) -> SaveIntent`, `layout(&self) -> &WorkflowLayout`, and `inspection(&self) -> &DefinitionInspection`. No caller-supplied report, status, identity or authority is trusted.

Public `SaveIntent` has exactly Rust variants `Draft` and `Validated`, derives Copy/Clone/Debug/PartialEq/Eq, and serializes/deserializes only the strings `draft` and `validated`. `WorkflowLayout` has private fields, Serialize but no Deserialize, `positions(&self) -> &[NodePosition]`, and `serialized_bytes(&self) -> Result<Vec<u8>, RecordError>` returning the canonical sorted layout JSON within 16 KiB. Public `NodePosition` is a Clone/Debug/PartialEq/Eq/Serialize value with exactly public Rust fields `node_index: u32`, `x: i64`, `y: i64`; its wire names are `nodeIndex,x,y` in that order. Exposing a position value does not permit mutation through an immutable record/layout getter. `WorkflowRevision::serialized_bytes()` returns canonical complete record JSON within 160 KiB; canonical definition bytes remain accessible through `inspection().canonical_definition_bytes()`. All canonical serializers preserve the same validated owned values; they do not rerun external resolution or mutate a record.

The record wire object is `schemaVersion,id,workflowId,parentRevisionId,intent,definition,layout` in that serialization order. The schema is exactly `rangoon.workflow-revision.v1`; parent is an explicit nullable `workflow-revision:` ID. Every wire field is required, including the nullable parent; missing fields never acquire implicit defaults. Workflow/revision IDs use their exact prefix plus 64 lowercase hex digits. `SaveIntent` is closed `draft` or `validated`. Intent describes the requested storage mode; a portable candidate does not claim successful persistence or resolved references. `validated` requires W1 structural validity immediately, and the later store must additionally resolve every dependency in its own transaction before accepting it. `draft` preserves any W1-decodable definition, including duplicate IDs, incomplete ports, missing references and graph errors. Both remain inert, with the W1 report's reference status unverified, execution unavailable and authority none.

`definition` is the nested W1 wire definition, not a JSON string or report. Its canonical member order, array/string preservation and byte bounds are exactly W1. A record may contain an invalid draft without a W1 definition identity. Decode canonicalizes object key order and whitespace but never repairs content, changes array order or normalizes text. An incorrect supplied revision ID is rejected after recomputation. Unknown fields, duplicate keys at any depth (including escaped-equivalent names), wrong field types, unknown variants, invalid UTF-8, trailing input and unsupported schemas are closed errors.

### Presentation layout

Layout is exactly `{positions:[{nodeIndex,x,y},...]}`. `nodeIndex` is a zero-based integer into the definition's current node array; this supports incomplete drafts with duplicate/invalid node IDs. Decode nodeIndex as u32 and coordinates as i64 JSON integers (fractions, wrong types and numeric overflow of those wire types are invalid JSON for this contract). Coordinates must then lie in the inclusive range -100000 through 100000. At most 128 entries; each index occurs once and is within the current node array. Entries serialize sorted by nodeIndex so input position-entry order does not change revision identity. Missing positions request automatic layout. No viewport, zoom, animation, theme, arbitrary style, URL, HTML or executable field is stored. Later editor insert/remove/reorder operations must remap indices in the same controller transaction as the definition edit; layout is never reused against a different node array without that remapping.

`prepare_revision` accepts layout JSON at most 16 KiB and rejects unknown/duplicate fields, invalid integers, repeated/out-of-range indices, overlarge coordinates and excessive nesting before returning a record. An empty positions array is valid, including for an empty draft. The canonical layout obeys the same compact UTF-8/escaping conventions as W1. Layout changes alter revision identity while preserving the W1 definition identity. This is saved presentation state, not graph execution order.

### Identity, bounds and failure

Revision identity is `workflow-revision:` plus lowercase SHA-256 over `rangoon.workflow-revision.v1\0` followed by five independently length-framed byte fields: workflow ID, parent ID (empty for None), intent's lowercase wire string, canonical W1 definition JSON, canonical layout JSON. Each length is unsigned big-endian u64. The record schema/id are not recursively included. A parent is a reference only; W2a cannot prove it exists, belongs to this workflow or is current. W2b must prove all three. Clock metadata is owned by the later store and excluded from these identities; it must never be represented as authenticated time.

Raw record input and canonical serialized record are each capped at 160 KiB. `prepare_revision` separately bounds its raw definition/layout arguments at 128/16 KiB. `decode_revision` bounds the whole raw record, then bounds canonicalized nested definition/layout bytes at 128/16 KiB; whitespace inside a nested object is subject to the whole-record raw limit, not a separate raw-subtree limit. Definition inspection still receives the bounded canonical W1 bytes. JSON container nesting is at most 32 counting the record or layout root as one. Check raw limits before decoding, keep strict duplicate-key scanning, reject excessive layout collections before sorting/traversal, and reuse the W1 inspector for definition validation. Allocation remains proportional to bounded input plus bounded typed collections, not an assertion that total memory equals the wire limit. No filesystem, database, network, clock, randomness source, process, provider or engine dependency is added.

`RecordError` is closed. `code()` and Display return exactly one of `input_limit`, `invalid_encoding`, `invalid_json`, `unsupported_schema`, `invalid_workflow_id`, `invalid_parent_id`, `invalid_revision_id`, `definition_invalid`, `layout_invalid`, `depth_limit`, `validated_definition_required`, `identity_mismatch`, `serialization_limit`, `serialization_failed`. `definition_invalid` wraps W1 decoding/resource failures without echoing text. In `prepare_revision`, any W1 inspection failure maps to it; in `decode_revision`, the strict typed record decoder first maps malformed nested fields/types/variants to `invalid_json`, then W1 inspection of the canonical nested definition can return `definition_invalid` (including wrong W1 schema or size). Structurally invalid drafts are not this error. `input_limit` covers the raw record limit and the raw layout argument limit; raw definition overflow is a W1 inspection failure and maps to `definition_invalid`. Record/layout syntax scanning must not apply W1 named collection quotas to the entire envelope: nested definition resource limits are classified by W1 inspection after strict typed decoding, and layout counts are classified by layout validation. `layout_invalid` covers coordinate-range, repeated/out-of-range index and count faults after typed decoding; malformed JSON, missing/wrong-type fields or duplicate/unknown fields remain `invalid_json`. Error text never echoes imported strings or decoder messages.

## W2b required storage and recovery semantics

The controller's [workflow workspace contract](workflow-workspace.md) specifies exact SQL/manifest bytes and API DTOs for independent review before migration code. Portable W2a records alone are not a saved workspace. The following requirements are fixed:

- Stable owners and immutable revision rows must form a bounded single-parent chain, with one root and a current head per workflow. Preserve canonical record bytes, verify identities and parent ownership on read, and never silently repair malformed rows. Limits: 128 workflows, 32 revisions per workflow, 1024 workflow revisions total, and the existing 64 MiB SQLite ceiling. Reject rather than evict. Capability quotas remain independent.
- Draft revisions may retain unresolved syntactically valid dependency references and show them as unresolved. A validated-intent revision requires structurally valid content and all exact capability/revision pairs in the final workspace. Do not mutate the pure W1 report into an authority claim. Pinned historical skill revisions remain pinned when the skill head advances.
- Every surviving workflow history reference with a syntactically valid capability ID to an existing capability blocks deleting that capability, including draft references whose revision ID is invalid or unresolved. A draft reference already absent may remain unresolved; deletion must not turn a previously resolved dependency into a silent missing reference. Workflow deletion removes its own complete history only, never its input skills/sources or another workflow. Confirm exact counts and expected full workspace state.
- Creation and revision saves are explicit, transactional and expected-head guarded. Exact retry/no-op behavior must be specified before implementation. Reads and previews never create or migrate stores. Introduce the next supported schema only with explicit save/restore, atomic migration and rollback evidence. Old binaries must reject it.
- Extend full-state identity, inventory/counts, validated record loading, and all source/capability/composition mutation paths. Audit every exact-version branch before accepting a new schema globally; legacy backup projections must never omit workflow records or downgrade a workspace.
- Add a new closed portable backup version with canonical workflow records and metadata. Keep V1/V2 decoder compatibility. Restore is additive: preserve existing workflow heads and complete histories; import absent workflows with complete histories. Verify the final union, including validated workflow dependencies whose pinned skill revision may be absent from a preserved local skill history. Reject such a restore atomically; never downgrade the record intent, switch to latest revision, or append old history silently.
- Migration, save, restore and deletion must preserve previous records under stale requests, quotas, disk-full and interrupted transactions. No writer is publishable before recovery and dependency-aware deletion pass independent review and targeted failure tests. Workspace remains unencrypted; identities prove internal consistency, not authenticity or tamperproof custody.

## W2c/W3 integration requirements

Native commands accept bounded definition/layout bytes and IDs, never renderer-supplied filesystem paths or SQL. The native session owns new-workflow identity issuance and exact preview/confirmation custody where needed. UI saves drafts separately from validation-dependent actions. Failures preserve current text, selection, layout and undo history; stale saves require explicit refresh/reconciliation, not automatic retry. Historical revisions are inspectable without silently making them current. Original workflow library/canvas/inspector hierarchy and keyboard/context-menu alternatives remain required. Qualify real native restart, backup, restore, stale-head and deletion behavior, plus dark/light 320/768/1440 states and all three desktop OSs separately from source CI.
