Recommend a versioned REST adapter to a separately supervised Agent Server for the first test, leaving Python and agent internals outside the Rust/Tauri process. SDK is the engine behind that service; embedding a Python interpreter is unnecessary. Codex is the initiating client/test controller, OpenHands is the executor. A restricted Rangoon MCP entry can be mounted later over the same adapter; no such Rangoon MCP server exists today. Do not assume OpenHands exposes every required operation through MCP or that Codex subscription credentials can be reused as OpenHands model credentials.

## Architectural advantages and faults

**Rangoon advantages:** pure transformation crates are reusable without desktop/provider I/O; Rust/store owns authoritative saved-reference resolution and transactions; immutable identities make review and reproducible input selection possible; provider observations do not silently become execution authority. This is a sound control/workbench boundary to preserve.

**Rangoon gaps:** no qualified durable execution path, task-to-runtime identity mapping or end-to-end proof of effective target configuration; native/provider support is narrower than preview surface area; content storage limits are unsuitable for operational logs; exported instructions do not establish enforcement. Introducing a second agent loop, queue, scheduler and copied event history would increase consistency and recovery burden. Keep one native execution owner and store only necessary Rangoon intent, links, reviews and reconciliation data.

**OpenHands advantages:** concrete conversation execution, supported remote control APIs, event persistence and separate automation lifecycle already exist in the inspected releases. These can eliminate substantial proposed custom work, subject to actual integration tests.

**OpenHands fit risks, not a full vulnerability audit:**

- [Direct `execute_tool`](https://github.com/OpenHands/software-agent-sdk/blob/38b6cdcc825df69ffdfe9c50e6635705612575ba/openhands-sdk/openhands/sdk/conversation/base.py#L410) explicitly bypasses agent-loop confirmation/security analysis. Terminal/bash/file APIs and another holder of server credentials may also lie outside the one controlled conversation path. A confirmation setting is not universal mediation.
- [ConfirmationResponseRequest](https://github.com/OpenHands/software-agent-sdk/blob/38b6cdcc825df69ffdfe9c50e6635705612575ba/openhands-agent-server/openhands/agent_server/models.py#L438) contains `accept` and `reason`, not an expected action digest/version. [Acceptance](https://github.com/OpenHands/software-agent-sdk/blob/38b6cdcc825df69ffdfe9c50e6635705612575ba/openhands-agent-server/openhands/agent_server/event_service.py#L2081) calls run; an already-running result is treated as no-op success. The inspected API does not establish atomic compare-and-authorize for the exact action shown in Rangoon. Pre/post readback alone cannot close that race. Strict per-action authorization remains unsupported unless a qualified native/mediated tool boundary provides it.
- SDK state defaults to `NeverConfirm`; local persistence can be disabled. Explicit configuration and effective readback are required. A risk classifier is advisory; it is not an external permission engine.
- [Automation local backend](https://github.com/OpenHands/automation/blob/850c66835a8176f30c6b0eaf75ca8b656191dad2/openhands/automation/backends/local.py#L57) uses an externally managed server and workspace directories; it creates no per-run sandbox. Directory separation is not process/network isolation. [Cancellation](https://github.com/OpenHands/automation/blob/850c66835a8176f30c6b0eaf75ca8b656191dad2/openhands/automation/router.py#L1441) records state and may schedule sandbox cleanup; that is not independently verified process termination or rollback.
- Server secret-field encryption is not whole-event/workspace/log encryption. Service authentication, output confidentiality, telemetry consent, storage retention, dependencies and actual OS/container confinement need explicit pilot configuration and tests. No throughput, high availability, multi-tenant safety or three-OS qualification was measured here.

## Can Rangoon govern an OpenHands task?

Yes for task admission, reviewed inputs/configuration, placement constraints actually enforced by the runtime, result inspection and evidence retention. Not yet for a blanket claim that every OpenHands tool action is authorized by Rangoon or LNSAT.

The proposed boundary is: authenticated caller → Rangoon task admission and immutable input/profile manifest → replaceable adapter → OpenHands conversation in a qualified confined runtime → native events/results → Rangoon evidence/reconciliation. Retain native conversation/action IDs and payload provenance alongside local review records. Mark each control as local admission, native confirmation, runtime-enforced, observed, unsupported or unknown. A task being admitted, a model reporting success, a native confirmation accepted and an externally verified effect are distinct records.

Do not expose Agent Server credentials or general execution endpoints to the renderer/model. Restrict client access and keep supervisor secrets/control sockets outside executed code. A prompt or API allowlist is insufficient if the task has equivalent host privileges. Use OS/runtime enforcement and externally scoped resource credentials; a later LNSAT-mediated consequential tool must independently prevent alternate routes. Neither LNSAT nor VUSL is required for authoring or this limited adapter evaluation, and no LNSAT/VUSL implementation change is proposed.

## One isolated Codex-controlled test packet — proposed, not executed

Owner: Root controls identity/security, adapter semantics, integration and validation. One bounded worker may later own only named fixture/test files; fresh independent reviewer checks the exact packet. Freeze exact source files and validators before implementation. Do not install or start the downloaded sources under this assessment.

Use a disposable synthetic repository and a separately owned sandboxed Agent Server, pinned release/image digest, explicit persistence and no host home, production paths, inherited credentials or control sockets. Initially use a deterministic local mock model with a fixed tool plan to exercise real OpenHands execution without paid inference; label this transport/execution proof, not autonomous model-quality proof. A genuine model run needs separate funding/credential/egress consent. Codex can drive the fixture harness; Rangoon MCP mounting is a later separately accepted source slice.

1. Create one Rangoon task/attempt identity and exported instruction/source manifest. Denied admission must cause no executor dispatch. Admitted submission maps durably to exactly one native conversation; duplicate/conflicting submission is checked.
2. Read back effective tool set, context/configuration and confirmation policy; compare retained instruction bytes where the native API exposes them. Report unavailable readback and semantic loss explicitly. No portability pass based only on matching an export hash.
3. Run an allowlisted validator against disposable source. Prove denied host-file, credential, socket/metadata and unapproved-egress probes with synthetic canaries. Mutation of source/execution identities before launch must refuse.
4. Exercise native rejection and approval with retained pending-action evidence. Label them native confirmation only; inject changed/stale pending state to demonstrate that unqualified exact-action approval is refused by Rangoon, not falsely declared enforced.
5. Disconnect Codex/client, reconnect and retrieve the same native conversation/events/artifacts. Restart the service, then reconcile instead of automatically re-executing; capture event gaps/duplicates and saved-message/run-capacity failures. Agent Server documents that a message may be saved before a 429, so retry run rather than blindly resending the message.
6. Cancel during a running tool and independently observe process/descendant termination. Preserve unknown if termination is not established. Capture result/artifact digests, native errors and retained storage/cleanup evidence.

Acceptance: pass task admission, actual confined execution, effective configuration/readback within explicit coverage, stable identity/reconnect and honest cancellation/evidence. Strict per-action authorization cannot pass on the current unbound confirmation API alone. A missing mandatory control blocks that scope. If OpenHands passes the bounded test, prefer it as the first execution adapter; evaluate Automation independently when scheduled work is actually needed. If it fails, implement only the evidenced missing capability behind a replaceable adapter or seek a supported upstream extension. No custom agent platform, automatic provider fallback or parallel scheduler is justified by this comparison.
