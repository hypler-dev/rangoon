# Specification: independent LNSAT evidence connector candidate

Status: proposed
Intent: [VUSL design request](intent.md#universal-systems-language-design-request--october-16-2026)
Owner: Jeff
Last updated: 2026-10-18

This is proposed D3: an **optional, read-only LNSAT evidence connector** for an exact operator-selected object. It refines the [accepted A1 boundary](engine-integration.md), [provider-neutral inspection contract](provider-interoperability.md), and [operator-record target](operations-control-plane.md#cross-runtime-operator-record-acceptance-target). It replaces none of them. Rangoon's local import, source provenance, revision, composition, compilation, export, and inspection must work with no LNSAT installation or connection. LNSAT alone owns authorization, approval, consumption, execution admission, receipts, and reconciliation.

### User job and scope

An operator selects one explicit LNSAT installation/profile, environment, and exact operation ID. Rangoon may later show the engine's native authorization, attempt, receipt, and already-recorded reconciliation readback with native IDs, contract/version, source time, read time, redaction, and coverage. It must preserve distinctions among request/evaluation, human approval, issued authorization, consumed authorization, attempted effect, reported receipt, and independently verified consequence. A valid grant is not a completed effect; no receipt or a failed read does not prove non-execution. LNSAT evidence never becomes Rangoon's own approval or a permission for Rangoon to execute.

OpenShell is a separate connector. LNSAT readback works without OpenShell; an OpenShell runtime observation works without LNSAT. Identical trace strings, timestamps, display names, native IDs, or user-selected objects do not join their facts. Cross-engine linkage requires an explicit, source-qualified bridge relation with a stable exact action/artifact binding and independent review. Missing bridge means two visible parallel records.

| Candidate operation | Meaning | D3 boundary |

| `describe_profile` | Offline pinned product, contract, source objects, privileges, limits and release qualification. | No connection or support claim. |
| `validate_configuration` | Check explicit endpoint/profile shape and display planned data classes. | Local only; no credential probe, installation discovery or engine configuration write. |
| `check_connection` | Explicit user-triggered protected read using a separately provisioned least-privilege identity. | Distinguish reachable from authenticated, compatible, authorized for exact read, and qualified for a selected environment. A health response proves none of the latter. |
| `read_exact_operation` | Request one exact operation, then its referenced exact authorization and optional attempt, only when the selected source allows each read. | GET only. Bind every returned object to the selected installation, environment, operation and exact reference. Never broaden to enumeration or follow arbitrary response URLs. |
| `read_exact_evidence` | Future exact approval/audit object read where LNSAT offers an authorized stable route. | Separate permission and reviewed native schema; do not infer full approval chain from operation fields. Unsupported until pinned. |

Reuse I1's provider identity/version/compatibility and evidence-provenance concepts, A1's closed unavailable operation boundary, and O1/O2's existing local observation records and presentation. D3 needs an LNSAT-native decoder/mapper and conformance fixtures, not a second generic integration envelope or independent authority engine. The proposed D0a VUSL profile admits only unverified policy/runtime observations; it has **no authorization, approval, receipt, or authenticated-ingress variant**. Do not force these LNSAT objects into D0a or set `authenticity=verified` on a D0a document. Keep qualified native evidence in the selected host custody until a later separately reviewed VUSL authority/evidence profile and trusted ingress exist.

For each native fact retain its source-qualified installation/environment/engine ID, product and wire contract, native object ID, object kind, referenced IDs, source timestamp and read timestamp, version/revision if actually supplied, payload digest or explicit omission, transport/authentication status, and adapter/profile version. Preserve native bytes only under an accepted encrypted-custody, redaction, retention, deletion and size policy with explicit consent. If native fields are omitted, transformed or unavailable, record that loss; never fill authority-critical fields from Rangoon UI state or another provider. A bounded canonical projection can add explanatory labels, not rewrite LNSAT decisions.

## States and failure handling

No provider configured, disconnected, unauthenticated, unauthorized, incompatible version, unsupported route, malformed native response, contradictory IDs, stale prior result, cancelled read, and unknown effect are distinct operator states. Failed refresh may retain a clearly stale last read for the same exact object, but may not display it as current, transfer it to another selected object, or silently retry a consequential operation. A timeout after a read says read outcome unknown; a timeout after any historical action says external effect remains unknown until qualified native readback and, if needed, independent target observation.

## Data, privacy, and permissions

Read only after explicit destination, data classes, object and retention consent. Require bounded requests/responses, local endpoint allowlist, TLS or reviewed loopback transport, redirect denial, strict JSON/contract validation, least-privilege session handling and fixed non-echoing errors. Do not scan ports, discover servers, read LNSAT's SQLite, invoke a CLI, start a daemon, or send project/source payloads with a connection check. On consent revocation, stop reads and purge retained sensitive bytes according to the selected encrypted workspace policy; retained minimal provenance must say whether evidence was removed. Three desktop OS clients need separate native qualification. A browser fixture or macOS source test cannot prove them.

## Compatibility and migration

A1 remains frozen and unavailable. D3 adds a separately versioned native-evidence profile after acceptance; it does not overwrite A1, I1, O1/O2 or existing encrypted workspace records. Unknown product or wire contract, changed identity/permission semantics, or a critical native field that cannot be preserved blocks the affected translation. Native bytes and historical provenance remain under their own custody policy; removing a D3 view must not change LNSAT data or reinterpret an older record as a current decision. Existing O0 combined-path fixtures are not migrated into D3.
