## Reconciliation and release boundary

Rangoon and LNSAT are separate products. Rangoon owns capability authoring, immutable source provenance, decomposition, composition, revisions, instruction compilation, export and inspection. These local workflows must start and remain usable without LNSAT or any other external provider installed, configured or running. A bundled inert diagnostic crate is not an installed external engine. An absent integration affects only its own optional operation; it cannot prevent local startup, reading, editing, recovery or export.

This makes the existing architecture's content/authority separation explicit rather than replacing useful implementation. Keep the current local store, composition/compiler/bundle APIs, optional model consent boundaries and all-three-desktop release path. Preserve the frozen [A1 LNSAT contract](engine-integration.md), current schemas and [operations inspection contracts](operations-control-plane.md). The proposed envelope below handles integration metadata and provenance; it neither replaces those contracts nor reimplements a provider's policy or identity semantics.

Approval management, telemetry and operations visualization remain accepted product scope. Complete their actual local views and honest unavailable states on their own track. Broad provider coverage, a live LNSAT endpoint and qualified governed execution are not prerequisites for shipping a useful qualified local workbench. Qualify each optional connected/enforced path separately and publish its exact coverage. No local release may advertise missing operations as supported.

## Small neutral contract

Use one small application-owned envelope, not a universal authorization API. The following is a proposed shape for I1, not a shipped schema:

- **Provider descriptor:** integration-instance ID, provider family, exact product target, adapter ID/version/digest, expected product version/artifact and protocol/schema pin, separately nullable observed product/contract, compatibility evidence reference and operation-specific capability states. A configured or documented version is not an observed version. Unsupported/missing pins never imply compatibility.
- **Configuration preview:** selected profile and exact configuration bytes/digest, supported schema/subset, diagnostics and explicit validation level (`local_shape` versus `provider_validated`). Preserve unrecognized provider concepts as unsupported; do not claim full native policy validity from JSON/YAML shape checks. Preview never applies, activates, admits or executes configuration.
- **Operation intent:** closed operations `configuration_preview`, `connection_check`, `evidence_read`, `authorization_evaluation` and `guardrail_evaluation`. A provider need not implement any particular operation. Exact lookup is used only when supported; no invented global list/search route. Evaluation is a separate explicit request, not mislabeled as source-free connectivity.
- **Operation state:** `unavailable` for an absent adapter or unavailable facility; `unsupported` for an operation or pin outside a profile; `disconnected` for a configured transport with no established connection; `error` for a failed/malformed attempt; `inspected` for a validated read/preview result. Reasons and nullable compatibility/connection observations remain separate. Healthy/reachable never means approved or enforced.
- **Evidence envelope:** provider/adapter/pin, operation, exact external record reference when supplied, input/configuration and response digests, reported policy revision/request/trace/resource references when available, observation versus receipt time, original provider schema/outcome, redaction/omission state, and explicit authenticity/freshness evidence. Missing fields remain unknown; never manufacture shared IDs, human identity or provider capabilities.
- **Provenance kind:** distinguish `provider_configuration`, `provider_decision`, `provider_guardrail_result`, `provider_approval`, `provider_execution_outcome` and `local_content_review`. Retain the provider-specific interpretation. An allow effect, no guardrail violations, local review or connection success cannot create an approval record or permission to execute. A provider's approval is not Rangoon's local review; an execution outcome requires separate evidence.

For the first read-only packet every output fixes Rangoon authority to `none`, execution to `unavailable`, and authenticity to `unverified`; no executable grant/success constructor or convenience `isAllowed()` exists. Provider-supplied outcome strings are namespaced reported data. Later authenticated readback may add explicit verification evidence through a reviewed revision; it cannot silently widen this contract. Digests establish identity/internal consistency only, not authenticity or tamperproof storage. No automatic conversion into `rangoon.ops` approval/authorization records: a future mapping must be versioned, loss-aware and independently reviewed.

Bound the first envelope/fixture input and serialized output to 256 KiB each, depth 16, 4,096 values, 32 fields per object, 128 array items, 64 diagnostics/references and 128-byte identifier tokens. Reject duplicate/unknown envelope fields, invalid UTF-8, unknown schema/pins, overflow and mismatched request/profile/digests with fixed payload-free errors, atomically. Provider payload is a bounded versioned document, not an executable object or a generic URL/command. The exact I1 subset, canonical ordering and error vocabulary are frozen below; do not add a general-purpose plugin runtime.

Non-inspected states require every field from `kind` onward to be null except `redaction=omitted`; no outcome/payload may hide behind an error. For inspected results, redaction is `none`, `redacted` or `omitted`. Non-omitted payload is a non-null bounded JSON value with exact SHA-256 of its canonical JSON. Omitted payload/digest are null. For inspected results only, `originalDigest` is required for redacted/omitted evidence and forbidden for none; non-inspected results keep it null under the previous rule. This is explicitly a reported original digest; it is never verified by retained redacted bytes. Configuration previews require payload to equal the parsed selected configuration JSON; its digest still identifies canonical JSON while configurationDigest preserves the exact original string bytes. Only an inspected configuration preview parses configuration, after observation payload-digest validation; other operations retain it as opaque UTF-8 bytes. This nested parse uses the same JSON scanner and integer/duplicate/depth/value/collection rules and error codes as the outer envelope. A valid parsed configuration unequal to payload fails `context_mismatch`. Preview validates JSON shape only, not a real provider policy. Inspection does not run policy text, detector code or tool arguments. Payload content is caller-selected and not automatically redacted; no diagnostics reflect it.

All digests are exactly 64 lowercase hexadecimal characters. Canonical JSON sorts every object key lexicographically, preserves array order and string content, uses serde_json compact encoding under existing pinned versions, and accepts only integer numbers with absolute value at most 9,007,199,254,740,991 (no decimal/exponent input). Whitespace and object-key order do not change canonical identity; original configuration string bytes remain unchanged. Duplicate keys including escaped equivalents are rejected before ordinary JSON materialization, including inside arbitrary payloads.
