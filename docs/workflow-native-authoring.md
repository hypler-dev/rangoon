# Native workflow authoring custody

Authority: the accepted workflow authoring sequence in [intent.md](intent.md). This W2c-2 contract exposes the published W1/W2a/W2b authoring lifecycle after [complete Data controls](workflow-native-controls.md). Acceptance, source checks, interactive qualification and publication receipts belong only in [development.md](development.md). The real W3 editor follows this seam; this packet does not replace the synthetic Workflows view or implement execution.

## Outcome and boundary

A native authoring session can start a new workflow identity or append to an explicitly selected current head, inspect an exact bounded definition/layout as a draft or validated candidate, and commit only the inspected retained candidate after explicit acknowledgment. Listing and historical opening are read-only. New identities, draft handles and save-preview handles are native-generated. Creation of a draft or inspection does not create a workspace. Only confirmed store saves can create/migrate schema 4, through the already qualified complete-state lifecycle.

Imported definition strings, titles, IDs, layout and diagnostics remain untrusted local data. Validated save intent means structurally valid with exact resolved local capability pins; it does not record review, approval, authentication, execution, LNSAT authority or government compliance. No provider, network, engine or process operation is introduced. Sources and the local SQLite workspace remain unencrypted.

## Commands and closed wire requests

Register six main-window-only local commands, retaining the existing shared workspace operation guard. List/open use blocking read helpers; begin/inspect/commit/clear are guarded to serialize draft and candidate replacement against writes/pickers. A locked operation reports the established fixed `workspace_busy` error and never discards an editor draft.

- `list_workflows()` calls the complete store inventory API. It returns `Listed { workflows }` without generating a draft session or inventing an empty result on failure.
- `open_workflow(raw)` takes `{schemaVersion:"rangoon.workflow-open.v1",workflowId,selection}`. Selection is exactly `{kind:"head"}` or `{kind:"historical",revisionId}`. It returns `Opened { workflow: WorkflowDetail }`; historical reading never changes the owner head or active native draft.
- `begin_workflow_draft(raw)` takes `{schemaVersion:"rangoon.workflow-draft.v1",target}`. Target is exactly `{kind:"new"}` or `{kind:"append",workflowId,expectedHeadId}`. For append, reopen the current head and require equality with the selected head before issuing the session. Return `DraftReady {schemaVersion:"rangoon.workflow-draft-session.v1",draftId,workflowId,parentRevisionId,workflow}`; `workflow` is the opened current detail for append or null for new. A new owner uses `workflow_id_from_nonce` over a fresh native 32-byte nonce. A `workflow-draft:` handle uses a separate fresh random 32-byte value. One successfully issued draft replaces the prior draft and its preview; failed beginning preserves them.
- `inspect_workflow_save(raw)` takes `{schemaVersion:"rangoon.workflow-inspect.v1",draftId,intent,definition,layout}`. Intent is exactly `draft` or `validated`. Retain definition/layout as raw JSON values, rather than converting through a permissive JSON object that discards duplicate fields. Enforce domain limits and use `prepare_revision` with the retained native workflow/parent identity. Re-resolve the candidate using `inspect_workflow_save` from the store. Return `SaveReady {schemaVersion:"rangoon.workflow-save-session.v1",draftId,previewId,revision,report,plan}` with the canonical immutable revision, structural report and exact complete store plan. A successful new preview replaces the prior candidate; failed inspection preserves it natively, while any future renderer treats uncertain preparation as stale.
- `commit_workflow_save(raw)` takes `{schemaVersion:"rangoon.workflow-commit.v1",previewId,expectedStateId,acknowledged}`. Acknowledgment must be true. Select and atomically take the exact retained canonical candidate and full plan before any store read/write. Reinspect and require exact plan equality, except the precise current-head no-op case specified below, then call the complete `save_workflow` transaction with the retained state. Return `Saved { receipt: WorkflowSaveReceipt }` only after confirmed success. Mismatched/unissued handles or states do not consume a different valid candidate. Matching confirmation consumes one attempt on success, refusal, callback failure or uncertain return; a fresh preview is required for another attempt. Never retry writes automatically.
- `clear_workflow_draft(raw)` takes `{schemaVersion:"rangoon.workflow-clear.v1",draftId}`. Clear only the matching active draft and its preview, returning `Cleared`. A mismatched handle cannot clear a newer session. No persistent record is deleted; Data controls remain responsible for explicit deletion.

Open/begin/commit/clear envelopes are at most 1 KiB. Inspection envelope is at most 160 KiB before deserialization; its embedded definition remains at most 128 KiB and raw layout at most 16 KiB through W1/W2a checks. Require UTF-8, exact schemas, required fields, closed fields/types/enums, no duplicate outer keys and exact lowercase 64-hex handle/record ID suffixes. Domain decoders enforce embedded duplicate-key, depth, resource, layout and identity rules. Tauri has already received the buffer: these source limits are not a transport-size guarantee. JSON arguments are refused; accepted bodies are raw UTF-8 JSON only.

## Retention, stale heads and uncertainty

Retain at most one draft context and one save candidate in separate application-owned session state. The context contains native draft/workflow identity and pinned parent; the candidate contains the exact `WorkflowRevision`, complete `WorkflowSavePlan` and opaque preview handle. Do not add Deserialize/public constructors to private domain/store values. The renderer supplies draft selectors and authored definition/layout, never a workflow ID, parent, revision ID, SQL, path, timestamp or store plan for save preparation.

The store plan must match the candidate's workflow/revision identity and the retained parent relationship. Normally expected head equals the pinned parent. The only exception is the store's precise existing-current-head retry: `alreadySaved:true` with expected head equal to the candidate ID. A historical match, moved head, deleted owner, changed dependency or stale state does not silently retarget/rebase. Native confirmation reinspection binds every field in the retained store plan, including its unresolved-reference count. The plan does not expose each dependency status. The sole post-reinspection equality exception is a store-issued `alreadySaved:true` plan with the same schema, workflow ID, candidate revision ID and unresolved-reference count, whose expected head is that exact candidate ID. The store produces that flag only after checking current-head canonical bytes against the retained candidate. Expected state/head and retry flag may then differ from the original plan because another writer saved the identical candidate; call the store with the retained original state, allowing only its precise no-op policy. A changed unresolved-reference count, historical match or different candidate still requires a fresh preview. Equal unresolved counts do not prove each dependency status is unchanged (for example, missing capability may become missing revision); the precise no-op receipt reports fresh reference statuses without mutating the stored candidate. The store immediate transaction retains concurrency revalidation: head movement/deletion before its read makes the no-op refusal safe. A concurrent exact candidate commit may also occur after native reinspection and make the final store result a no-op. Neither case authorizes a different mutation or automatic write retry.

Taking a preview leaves its draft identity available for repair or a fresh explicit inspection. It does not change renderer text, selection, viewport or local undo history. A later W3 controller must preserve all unsaved state on invalid inspection, stale/error save and uncertain receipt, and must compare a saved receipt to the inspected candidate before accepting it. Successful append/reopen begins a fresh session pinned to the returned current head; no hidden native rebasing occurs. Clear is explicit; application shutdown drops in-memory sessions. Session handles are custody selectors, not authentication or proof of a human's decision.
