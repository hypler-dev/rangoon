# Native local-model session and consent

Authority: the October 6 model-assistance continuation in [intent.md](intent.md). This controller specification refines [model-assistance.md](model-assistance.md), the [pure context contract](model-context-core.md) and the [local transport contract](model-local-adapter.md). Implementation and validation status belong in [development.md](development.md). This document does not establish shipped GUI behavior or security qualification.

## Ownership and scope

The native process owns one session-only local profile, one prepared request and at most one active model operation. Restart forgets all three. No credentials, profiles, payloads or model results are written to disk by this feature. Durable profiles, cloud credential custody, proposal application and quality measurements remain required subsequent work. The saved source workspace retains its existing plaintext storage boundary. Memory-only custody does not promise secure heap erasure or protection from process inspection, swap or OS crash dumps.

Only the local `main` window receives narrow model commands. The renderer cannot supply a filesystem path, request URL, header, source text, digest, prompt, permission, approval boolean or transport options. Its CSP remains IPC-only. Native code uses `LocalProfile`, `prepare_pack`, `PreparedRequest` and `LocalClient`; it does not recreate their protocol or authority semantics. All results have authority `none`.

A compromised renderer can change visible UI, configure a loopback profile, request a source-free check and open a native confirmation. It cannot transmit source merely by asserting approval. A native dialog generated from retained native data makes the final transmission decision. This does not authenticate the loopback process, ensure local inference, prevent a malicious OS/native process, or establish freedom from UI deception. Loopback services can forward or retain data. No user-source validation is authorized by this development packet: use disposable synthetic workspaces and servers.

## Closed inputs

All commands with input accept only raw IPC bytes, checked before decoding. JSON objects reject duplicate/unknown fields, trailing data and incorrect types. Values must meet the existing profile or saved-ID validators. No generic JSON value supplied by the renderer reaches transport.

| Command | Input | Effect |
| --- | --- | --- |
| `get_local_model_profile` | No input | Return the configured profile and session-only/unknown-processing disclosures, or unconfigured |
| `configure_local_model` | Existing local-profile request, at most 1,024 bytes | Parse first, then replace profile and discard prepared request while idle; no I/O |
| `clear_local_model` | No input | Remove profile and prepared request; invalidate and cancel any active operation |
| `prepare_local_model` | Selector below, at most 8,192 bytes | Read explicitly selected saved records, create and retain exact request; no network |
| `check_local_model` | No input | Explicit source-free GET using the current profile; no startup or configure check |
| `send_local_model` | Confirmation below, at most 512 bytes | Claim a retained request once, show native confirmation, revalidate inputs and send exact bytes if still valid |
| `cancel_local_model` | Run selector below, at most 256 bytes | Cancel only the matching active operation; discard the session’s prepared request |

Selector schema is exactly `rangoon.local-selection.v1`, with fields `schemaVersion`, `task`, `inputs`. Task is `classify_v1`, `decompose_v1` or `compare_v1`. Inputs contain 1–16 distinct closed objects, each either `{kind:"source",sourceId}` or `{kind:"capability",capabilityId,revisionId}`. Compare requires exactly two explicit capability revisions; other tasks permit either kind. Duplicate references are invalid. Capability selection always names a revision; it never silently follows a head.

Confirmation schema is exactly `rangoon.local-send.v1`, with `schemaVersion`, `preparedId`, `requestId`. It does not contain an approval flag. Run selector schema is exactly `rangoon.local-cancel.v1`, with `schemaVersion`, `runId`. Handles are cryptographically random 32-byte values encoded as lowercase hex with `prepared:` or `run:` prefixes. They are session identities, not authentication or consent proof. Entropy failure is a closed session-unavailable error; no predictable fallback.

## Saved-record resolution and packing

Resolve sources through `Workspace::open` and capabilities through `Workspace::open_capability_v1` with the explicit revision. Existing validated store reads establish internal consistency, not authenticity against an attacker who can rewrite the workspace. Retain each exact input reference/digest and the capability's observed latest revision ID as a dependency. Do not transmit source filenames or local paths. Native scope is `saved-source` or `saved-capability-revision`; identities distinguish inputs sharing a scope.

The first native selection uses the full exact content of each record. Every nonempty input has one selection `[0, byteLength)` marked protected and the same required protected interval. Empty saved inputs fail explicitly with `input_empty`: the pure packer requires a nonempty selection, and the native layer never fabricates text or ranges. There is no heuristic or model-authored omission. Existing byte-identical deduplication may save repeated text while preserving all aliases and protected obligations. The pure and final transport byte limits still apply; over-budget data is rejected, never truncated. Exact tokens, cost, retention and inference location remain unknown.

Prepared output exposes `preparedId`, `requestId`, the immutable final `bodyJson`, origin, model, selected record references, observed heads, byte counts and pure pack accounting. No network occurs during prepare. New successful preparation replaces the prior prepared request. A failed preparation discards the old prepared request so the UI cannot accidentally reuse a prior selection.

Revalidation reads every retained dependency again and compares exact identities/digests, bytes and observed capability heads. Changed heads invalidate a prepared request even if its selected historical revision survives. Missing, corrupt or unavailable records fail closed before sending. New unrelated records do not invalidate it. Final revalidation uses the existing workspace-operation guard briefly; never hold that guard or a model-state mutex while waiting for a dialog or network. External filesystem writers remain outside the in-process guard, so this is a read-before-dispatch check, not an atomic guarantee against arbitrary concurrent disk mutation.

## Lifecycle and race handling

Profile generation is a checked monotonic counter. Overflow fails closed. Native session state lives behind short mutex sections. Operation ownership uses a random run ID, a cloned monotonic cancellation token and an RAII lease; dropping the operation releases only its own active slot. An old completion must not erase a newer prepared request or publish success after clear/cancel. No session mutex spans an await, blocking dialog, store read or network call.

Configure is allowed only while idle. Clear always invalidates the generation/profile/prepared request and cancels the active token; the active slot remains until that operation exits. Prepare/check/send reject while another operation is active. Inspection returns a decimal-string generation, incremented for each accepted configure/clear. Async command results must carry their captured generation and run ID; the renderer discards results from an older generation or superseded operation. Idle profile inspection returns the current profile; active inspection additionally returns run ID and operation kind so cancellation is possible without receiving a long-running command's result first.

Prepare reserves an active slot, captures profile/generation, clears old preparation, resolves records, packs and stages only if that lease still owns the current generation and is not cancelled. A cancelled/cleared preparation never stages a result. Cancellation of an unrelated/stale run returns `run_not_found` and never affects a newer operation.

Send checks the current prepared handle and exact request ID, consumes that preparation before opening the dialog, and reserves an active slot. All later outcomes consume that handle, including declined confirmation, cancellation, stale input, connection failure or lost IPC response. Retry requires prepare plus a new explicit decision; there is no replay, automatic retry or provider fallback.

The [native workbench refinement](model-native-workbench.md) defines the confirmation surface: an isolated native-created review window parented to `main`, containing the full selection metadata and exact request body, followed by a final OS Send/Cancel dialog parented to that review window. The refinement also freezes per-outcome IPC fields and review-only capabilities. Neither a renderer acknowledgment nor a prepared handle proves consent. The final native decision approves only the retained immutable request, after cancellation and source-freshness checks.

Cancellation while a native dialog is open records cancellation immediately; the operation remains active until the dialog closes. A later affirmative answer cannot resurrect the cancelled request. No native dialog-close guarantee is claimed. Clear behaves the same way. After affirmative confirmation, revalidate the profile/generation, acquire the workspace-operation guard, revalidate dependencies, and release the guard at the dispatch transition. If the workspace is busy, fail without waiting or sending. Recheck cancellation immediately before transport; the transport's own cancellation handling remains active throughout I/O.

After transport success, re-resolve dependencies before returning. If they changed or cannot be checked, return the validated completion with freshness `stale` or `unavailable`; it remains inspectable, advisory and ineligible for future application. Freshness `current` means the post-response read matched, not a permanent guarantee. An explicit cancellation or clear suppresses successful completion. Cancellation/timeout cannot recall bytes already transmitted or stop remote work reliably. Check results establish protocol reachability only and do not validate the configured model or authorize sending.

## Outcomes and validation

The foundation packet did not freeze the IPC envelope. The independently reviewed [native workbench refinement](model-native-workbench.md) now defines exact per-outcome fields, including `cancel_requested`, and null generation only when session inspection fails. The required envelope behavior is: `outcome` selects unconfigured, configured, cleared, prepared, checked, completed, cancel_requested, cancelled or failed; all results include `schemaVersion:"rangoon.local-session-result.v1"`, decimal-string `generation` (null only when session inspection fails), nullable `runId`, and `authority:"none"`. Synchronous idle results have null run IDs; every async result is attributed to its captured generation/run. Outcome-specific fields are frozen in the linked workbench contract and implemented by the native handlers. The portable service DTOs below are not that IPC envelope. Failures expose a bounded code, never source text, provider bodies, paths or dynamic error strings. Native diagnostic categories distinguish invalid request, invalid profile, unconfigured, busy, session unavailable, stale prepared request, run not found, input unavailable/empty/stale, pack invalid/over budget and published transport diagnostics. Completion includes its exact request ID and freshness. No response creates or reviews a capability or invokes LNSAT.

Required tests cover raw limits/types/unknown and duplicate fields; exact selected bytes including BOM/CRLF/Unicode; empty records; duplicate IDs; wrong revision ownership; source deletion/corruption; changed capability head; profile replacement; stale/replayed handles; missing entropy; cancel before/during/after prepare/check/dialog/send; clear while active; dropped leases; old completion ordering; and unrelated workspace changes. Synthetic transport tests exercise prepared exact bytes and no source before native approval. The workbench implements payload inspection, unknown token/retention disclosures, busy/cancel/error recovery and inert response rendering. Full native keyboard, screen-reader and reduced-motion qualification remains required. Native GUI checks must distinguish macOS evidence from Windows/Linux gaps.

Implementation sequence: the reviewed portable `rangoon-model-session` foundation was followed by native command/dialog integration and payload/proposal inspection UI. These are implemented, with bounded independently reviewed synthetic and macOS native evidence in the ledger. Remaining cross-platform, failure-state and accessibility qualification stays open; proposal application is not implemented. Rollback removes the new allowlisted commands/UI without changing saved workspace schema or identities. No actual model installation, launch, credentials, paid/private calls, engine activation, release or deployment is included.

## Portable service API in the foundation packet

`LocalSession` clones share memory behind one mutex. `configure`, `inspect`, `clear` and `cancel` expose profile/run lifecycle. `begin_prepare` returns a non-cloneable `Preparation`; its `prepare(&Workspace)` resolves saved inputs and stages an immutable request. `begin_check` returns an `Operation`. `begin_send` returns a non-cloneable `Transmission`, consumes a matched handle, and exposes the retained `PreparedRequest` to trusted native code. These service types are not deserializable authority objects. They do not send requests, show dialogs, acquire the desktop workspace guard or approve transmission.

`Operation` exposes run ID, captured decimal-string generation, immutable profile, monotonic cancellation token and `ensure_current`. Drop cancels the token and clears only its matching active slot. `Transmission::freshness` re-reads retained dependencies and returns current, stale or unavailable after checking operation validity on both sides of the read. Native orchestration must still enforce affirmative confirmation, pre-dispatch freshness and post-response attribution.

`SessionView` serializes generation, profile (or null), active `{runId,kind}` (or null), persistence `session_only`, processingLocation/retention `unknown` and authority `none`. `PreparedView` serializes generation, preparedId, requestId, origin, model, exact bodyJson/bodyBytes, inputs `{input,observedHead,byteLength}`, the published pure `pack`, processingLocation/retention `unknown` and authority `none`. IDs/digests and exact bytes are retained privately; mutating a serialized view cannot mutate native custody. A fresh `LocalSession` starts unconfigured with generation `0`. No source or schema writes occur while resolving, preparing or inspecting freshness.
