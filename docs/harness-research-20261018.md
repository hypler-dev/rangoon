## Rangoon's current position

Rangoon's strongest source-backed foundation is local source provenance, immutable revisions, deterministic composition and instruction exports. This is useful independently of a particular model or execution engine. It is not yet an end-to-end installed encrypted workbench, connected operator console, runtime scheduler, or evaluation platform.

| Need | Existing implementation to reuse | Missing or unqualified behavior |
| --- | --- | --- |
| Review and reuse capabilities | `rangoon-import`, `rangoon-store`, `rangoon-compose`, `rangoon-compile`; immutable skill/workflow revisions and exact export inspection | Complete encrypted adoption, selected real target-loader fidelity, repeatable installed tasks across three OSs; explicit-root discovery and durable organization remain planned |
| Efficient, attributable context | `rangoon-model-assistance/src/pack.rs` performs exact selection/deduplication, protected ranges and omission records; `response.rs`/`inspection.rs` retain citations and uncertainty | Token accounting remains unknown where no measured provider/tokenizer value exists. No measured semantic compression guarantee or cross-model quality comparison |
| Controlled optional inference | Local/cloud transport and session/native consent custody; provider-reported usage/duration fields where available | Qualified provider/version task evidence, cost reconciliation and repeatable model-upgrade evaluation; no implicit calls or fallback |
| Independent provider inspection | D1 offline observation parser, D2a OpenShell mapping, D3a LNSAT decoder, unmounted D2b OpenShell OIDC client and synthetic native custody tests | Production Start remains unavailable. Real target, native event loop, credentials, three-OS and source-specific evidence qualification remain separate |
| Runtime evidence | O1 observations and O2 selected-file projection; sequence/conflict/unknown states and read-only timelines | Authenticated ingress, trustworthy source relationships, O3 detail/provenance and real outcome reconciliation. A shared trace/digest is not proof that two engines refer to the same attempt |
| Task survival | Stored workflow definitions/revisions and separate observation records; model-session custody is memory-only | Durable wait/resume task semantics are not implemented. A saved definition does not represent a running task or prove recovery |
| Quality and efficiency regression | Golden vectors, deterministic conformance tests and fixture tests | User datasets, labeled outcomes, paired configuration experiments, ablations, evaluator agreement and regression promotion rules |
| Generated tools and portable runtime recipes | Existing revision, workflow, compilation, I1 descriptor and R9 SDK plans | Generated artifact admission/expiry/removal and portable task recipe/profile tests. Runtime installation and execution remain provider responsibilities |

## Focus and differentiation

Concentrate on **a capability change that can be explained, exported, compared and safely reverted across systems**. A useful product test is: select a skill revision, see its source and target losses, compare a proposed change against the same cases, and retain the evidence after a model or harness upgrade. No reviewed outcome currently proves a market advantage; pilot tasks must measure whether users prefer this workflow to Git plus their existing harness/evaluation tools.

The initial audience remains developers and small platform teams. Avoid simultaneously building a coding agent, general execution runtime, credential broker, observability backend and plugin marketplace. Those are separate mature or actively evolving categories. Their existence makes integration and precise differentiation more valuable, not less.

New requirements are ordered in [the canonical plan](plan.md#harness-value-and-portability-completion-track): finish the existing local/native path; add an offline evaluation record/fixture packet; then compaction fidelity and portable change evidence; later inspect external waiting/recovery and generated-capability lifecycle. The evidence model must retain uncertainty, failed attempts, omissions, measurement methods and native payload provenance. Security controls are not behavioral workarounds eligible for automatic removal.

## Product presentation

Use existing surfaces instead of adding more top-level menus. Skills and Compile gain a future Compare changes action; its inspector shows source, target, evaluation and export consequences. Test Lab owns datasets, baseline/candidate comparisons and regressions. Operations owns externally reported waiting/blocker/recovery states with provenance and clear unsupported actions. Advanced detail reveals model/runtime/adapter versions and measurement methods. No synthetic green score, fake running task or permission inferred from a graph edge.

## Research cadence and stop rules

For each candidate, record official source, pinned release/commit, observed date, affected contract, privacy/licensing change and regression cases before promotion. Recheck after model/harness upgrades and before adapter acceptance, not by continuously installing whatever is new. Maintain a small watchlist: Cursor context/tool loading, HarnessTax and Apple/EPFL evaluation methods, Phoenix/LangSmith evidence interchange, LangGraph checkpoint semantics, DeepSeek Harness/Cordis plugin lifecycle, Modal/OpenShell environment boundaries and Google's credential proxy constraints. Conference anecdotes remain hypotheses until tested.

Do not promise universal support, lower costs, millions of requests, secure self-modification or better results than competitors without a matching benchmark and deployment envelope. Preserve runtime semantics when importing evidence; unknown fields, unsupported versions, missing checkpoints and stale approvals remain visible and cannot silently downconvert.
