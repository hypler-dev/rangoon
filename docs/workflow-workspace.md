# Workflow workspace storage and recovery

Authority: accepted V1 authoring objective in [intent.md](intent.md), with immutable portable records defined by [workflow-records.md](workflow-records.md). This controller-owned W2b contract specifies the durable lifecycle before a writer is exposed. Evidence and acceptance checkpoints belong in [development.md](development.md). It does not authorize execution, LNSAT activation, provider use or released-platform claims.

## Outcome and staging

Explicitly saved workflows survive restart with exact definitions, node positions and complete immutable history. Incomplete typed drafts remain saveable. Saving with validated intent additionally requires all pinned capability revisions to exist in the same validated workspace. Neither mode grants content review, execution or approval authority.

Implement validated storage records first, then complete schema migration, save, backup, additive restore and dependency-aware deletion as one publishable lifecycle. Internal read-only foundations may be tested while the public schema gate still rejects version 4. Do not expose a version-4 writer or widen the global schema gate before the complete lifecycle and failure tests pass independent review. Native commands and the real editor follow in W2c/W3; they are not implemented by this store contract.

## Exact schema and immutable history

SQLite application ID stays `0x52474e31`. Version 4 consists of every exact schema-3 table plus these two exact SQL strings, with no additional indexes/triggers/views beyond SQLite's implicit primary-key indexes:

```sql
CREATE TABLE workflows (workflow_id TEXT PRIMARY KEY NOT NULL, latest_revision_id TEXT NOT NULL)
CREATE TABLE workflow_revisions (revision_id TEXT PRIMARY KEY NOT NULL, workflow_id TEXT NOT NULL, record_json BLOB NOT NULL, saved_at_ms INTEGER NOT NULL)
```

The canonical W2a record is the only definition/layout representation. Store compact canonical `WorkflowRevision::serialized_bytes()` bytes; reject noncanonical or malformed stored bytes rather than rewriting them. Row IDs/owner must match the decoded record. Recompute every revision identity. `saved_at_ms` is host clock metadata, excluded from revision identity, in inclusive range 0 through 8,640,000,000,000,000. It is not authenticated time; history order comes from parents, not timestamps. No timestamp monotonicity assumption is permitted.

Each owner has exactly one root and one head. Following the head's parent references must visit every revision belonging to that workflow exactly once and terminate at its sole null-parent root. Reject missing/cross-owner parents, cycles, forks, orphan rows, mismatched heads, empty owners and reused revision IDs. Never choose a head by timestamp. Bounds: 128 workflows, 32 revisions per workflow, 1,024 workflow revisions total, 160 KiB per canonical workflow record, existing 64 MiB SQLite allocation ceiling. Existing capability quotas remain separate. Check row counts and BLOB lengths before loading/decoding; enforce complete database/page limits before commit. The two-table minimum and indexes count toward allocation.

Every load validates all workflow histories and every validated-intent record's exact capability dependencies. Draft references may be invalid or unresolved. Iterate capability nodes by node-array index, preserving duplicate node IDs in drafts. Classify a reference as `invalid_reference` when either ID syntax is invalid; `missing_capability` when the owner is absent; `missing_revision` when the exact revision is absent or belongs to another owner; otherwise `resolved`. No head substitution or graph repair. Report these observations separately from the immutable W1 report, whose references stay unverified and authority stays none.

## State identity and read APIs

Schemas 1–3 keep the existing `workspace-state.v1` byte algorithm unchanged. Schema 4 serializes compact JSON of this tuple, in this exact order:

```text
["rangoon.workspace-state.v2", 4, sources, capabilityOwners,
 capabilityRevisions, recipes, applications, workflowOwners, workflowRevisions]
```

The first five collections after version use the current validated `Records::state_id` encodings: sorted source metadata array; owner map; revision-ID map to `[capabilityId, RevisionSummary]`; recipe-ID map to timestamp; application-ID map to `[compositionId,timestamp]`. Add workflow-ID map to head revision ID, then workflow-revision-ID map to `[workflowId,savedAtMs]`. All maps use ascending Rust string order. Validated canonical content is bound through recomputed IDs. Return `workspace:` plus lowercase SHA-256 of the complete tuple bytes. Metadata/head/history changes therefore invalidate state. This is a stale-state digest, not an authentication seal.

Public store methods return `Result<_, StoreError>` and never initialize/migrate during reads:

```rust
list_workflows(&self) -> Result<Vec<WorkflowSummary>, StoreError>
open_workflow(&self, workflow_id: &str, revision_id: Option<&str>) -> Result<WorkflowDetail, StoreError>
inspect_workflow_save(&self, candidate: &WorkflowRevision) -> Result<WorkflowSavePlan, StoreError>
save_workflow(&self, candidate: &WorkflowRevision, expected_state_id: &str) -> Result<WorkflowSaveReceipt, StoreError>
```

For missing workspaces, list returns empty; open returns `WorkflowNotFound`; save inspection uses the existing canonical empty schema-1 state. Explicit open revision must belong to the requested owner; None selects the current head. List order is workflow ID ascending. History summaries are root-to-head, not timestamp-sorted.

DTOs are Serialize-only, camelCase, with these exact field orders/types (Rust integer types shown; IDs and schema labels are strings):

- `WorkflowSummary`: `id,latestRevisionId,label,labelAdjusted,intent,structurallyValid,revisionCount,savedAtMs,unresolvedReferences`. Intent is W2a `SaveIntent`; booleans as named; counts u32; timestamp i64. Fields describe the current head. Label is display-only: remove characters matched by Rust `char::is_control` and U+2028/U+2029 from the original title, trim whitespace, retain at most 160 UTF-8 bytes ending at a character boundary, trim again, and use `Untitled workflow` if empty. `labelAdjusted` compares this display label to the exact original title. Original title bytes remain in the record.
- `WorkflowRevisionSummary`: `id,parentRevisionId,intent,structurallyValid,savedAtMs`. Parent is nullable, intent closed, validity bool, time i64.
- `WorkflowReference`: `nodeIndex,capabilityId,revisionId,status`. Index u32; exact imported ID strings; status is one of the four values above. Order is node-array order. Values remain untrusted source, never HTML or commands.
- `WorkflowDetail`: `schemaVersion,head,revision,savedAtMs,history,references`; schema `rangoon.workflow-detail.v1`; head is `WorkflowSummary`, revision is the selected canonical W2a object, history is `Vec<WorkflowRevisionSummary>` for the complete chain, references describe that selected revision. Historical inspection never advances the head.
- `WorkflowSavePlan`: `schemaVersion,workflowId,revisionId,expectedStateId,expectedHeadId,alreadySaved,unresolvedReferences`; schema `rangoon.workflow-save-plan.v1`, nullable head, bool retry flag, u32 unresolved count. Returned only after prospective full-state, dependency and allocation validation.
- `WorkflowSaveReceipt`: `schemaVersion,workflow,alreadySaved,stateId`; schema `rangoon.workflow-save-receipt.v1`; workflow is fresh `WorkflowDetail` for the saved/current head, bool retry flag, resulting complete state ID.

## Transaction, concurrency and retries

Validate candidate through W2a canonical serialization/decoding even though the public type has private fields. All writes acquire the existing immediate transaction, load/validate complete current state, recompute dependencies and quotas, and derive final records again. Preparation is not authority to trust renderer state or bypass transaction checks.

A new owner requires a null parent. Appending requires candidate parent equal to the current head. Creating with an occupied workflow ID and different root is a conflict, not deduplication. A supplied expected state must be a syntactically valid `workspace:` ID and equal the current full state, except the precise no-op case below. Stale state yields `WorkspaceChanged`; wrong parent/head yields `WorkflowConflict`. Do not silently rebase, retarget or retry.

Exact retry is allowed only when the current head is already the candidate ID and its stored canonical bytes match the candidate. Return `alreadySaved:true`, existing timestamp/history and fresh state without any row/head/schema change; a syntactically valid old expected-state ID is allowed for this no-op. All current rows/dependencies still must validate. A historical matching candidate whose owner head has moved is not a retry success. A deleted workflow cannot be recreated with an old expected state. New successful saves set one host timestamp, add one immutable row, update/create its owner and return `alreadySaved:false`. No-op does not consume quota or update clock metadata.

Before commit, validate the prospective full state and reconstruct its canonical SQLite allocation as with existing composition writes; preserve final actual page-count checks as well. Upgrade older schemas and insert new rows/head in the same transaction. Failure rolls back metadata and data together. A failed first write may leave the existing permitted empty SQLite file; it must not leave initialized partial tables. Keep the original file untouched on read/preview, unknown schema or rejected backup.

## Backup V3 exact format

Add `WorkspaceBackup` as a validated private-field archive type with `decode(&[u8])`, `id(&self)->&str`, `byte_length(&self)->usize`. Decoder explicitly routes V1/V2 through their existing decoders without changing their accepted bytes. V3 is plaintext and uses magic `RANGOON-BACKUP-V3\n`, four-byte big-endian manifest length, compact UTF-8 JSON manifest, ordered content payloads, then 64 lowercase ASCII SHA-256 hex bytes over everything before that trailer. Backup ID is `backup:` plus SHA-256 of the entire archive including trailer. Preserve the existing 68 MiB whole-archive and 2 MiB manifest caps; checked arithmetic and exact total-length equality precede any slice/allocation by declared length. Aggregate payload must not exceed 64 MiB; canonical reconstructed SQLite must also fit 64 MiB.

V3 manifest schema is `rangoon.backup.v3`. Exact field order: `schemaVersion,sources,owners,revisions,recipes,applications,workflows,workflowRevisions`. The first five record arrays preserve every V2 descriptor's field order, validation, bounds and identity behavior. `workflows` is at most 128 descriptors `{id,latestRevisionId}` sorted by workflow ID. `workflowRevisions` is at most 1024 descriptors `{id,workflowId,byteLength,sha256,savedAtMs}` sorted by revision ID; byteLength u32 <=160 KiB, digest lowercase SHA-256, timestamp i64 bounded as above. Each descriptor array is ascending and unique; missing/duplicate/unknown fields and noncanonical manifest bytes are rejected.

Payloads follow exactly: source content by source ID, capability revision content by revision ID, canonical recipe JSON by recipe ID, canonical workflow record JSON by workflow revision ID. No payload exists for workflow owners or applications. Validate declared bytes/digests and regenerate the complete canonical manifest after rebuilding/validating all records. V3 decoding validates/reconstructs schema 4 in memory, including when workflow arrays are empty; this does not migrate a destination. A no-additions restore preserves the destination schema without a write. V1/V2 archives keep their existing reconstruction behavior. Export a schema-4 workspace as V3; workflow-aware export of schemas 1–3 retains the existing V2 encoding. Legacy export APIs must reject schema 4 rather than omit its records.

## Versioned complete workspace/recovery APIs

Introduce these methods; legacy DTOs stay closed and unchanged:

```rust
workflow_data(&self) -> Result<WorkflowWorkspaceData, StoreError>
export_workflow_backup(&self) -> Result<Vec<u8>, StoreError>
prepare_workflow_restore(&self, backup: &WorkspaceBackup) -> Result<WorkflowRestorePlan, StoreError>
restore_workflow_backup(&self, backup: &WorkspaceBackup, plan: &WorkflowRestorePlan) -> Result<WorkflowWorkspaceData, StoreError>
inspect_workflow_deletion(&self, kind: WorkflowRecordKind, id: &str) -> Result<WorkflowDeletionPlan, StoreError>
delete_workflow_record(&self, plan: &WorkflowDeletionPlan) -> Result<WorkflowWorkspaceData, StoreError>
```

`WorkflowRecordKind` is exactly Source/Capability/Workflow with lowercase wire values. New Serialize-only DTOs use camelCase and the following field order:

- `WorkflowRecoveryCounts`: existing `sources,capabilities,revisions,reviews,recipes,applications,derivations` u32 counts followed by `workflows,workflowRevisions` u32. Never include workflow revisions in capability revision counts.
- `WorkflowWorkspaceData`: `schemaVersion,stateId,records,databaseBytes,reusableBytes,sources,capabilities,workflows`. Schema `rangoon.workspace-data.v2`; counts as above; byte fields u64; source/capability summaries keep existing types and order; workflow summaries sorted by ID. Absent workspace returns zero counts/lists and canonical empty state without creating anything.
- `WorkflowRestorePlan`: `schemaVersion,backupId,expectedStateId,byteLength,add,keptSources,keptCapabilities,keptWorkflows`. Schema `rangoon.restore-plan.v2`; byteLength usize; add full new counts; kept counts u32.
- `WorkflowDeletionPlan`: `schemaVersion,kind,id,label,expectedStateId,remove,capabilityDependencies,workflowDependencies`. Schema `rangoon.deletion-plan.v2`; new kind; label uses source display name, capability title or derived workflow display label; remove full counts; dependency arrays contain unique sorted existing capability/workflow summaries. A blocked plan remains inspectable and must describe only the prospective removal of the selected record/history, not delete dependents. Commit refuses any surviving dependent.

Restore/deletion plan fields are private, Clone/Debug/PartialEq/Eq/Serialize with no Deserialize or public constructor. `WorkflowRestorePlan` exposes `backup_id(&self)->&str` and `expected_state_id(&self)->&str`; `WorkflowDeletionPlan` exposes `expected_state_id(&self)->&str`, `kind(&self)->WorkflowRecordKind` and `id(&self)->&str`. Native code may serialize the complete plan and retain it; it cannot treat renderer-supplied fields as that retained plan. Commit reloads full state inside an immediate transaction, recomputes the complete plan from the retained backup or selected kind/ID, and requires full field equality, including backup identity/length, labels, counts, kept counts and dependency lists as applicable. Any mismatch returns WorkspaceChanged without mutation. This binds candidate data and impact; it does not authenticate a human decision. W2c must separately retain exact native confirmation custody.

Restore is additive at owner granularity. Preserve existing sources, capability owners with all current histories/reviews, and workflow owners with all current histories/heads. Import absent workflow owners only with their complete histories, never append backup history to a kept owner or change its head. For an existing workflow owner, the entire incoming root-to-head chain must be an exact prefix of the local chain, comparing canonical record bytes and stored timestamps. Identical chains and older matching prefixes are kept; count the owner as kept and add zero workflow revisions. Incoming newer, divergent, forked or metadata-mismatched history rejects the complete restore with BackupInvalid. Thus no incoming workflow revision is silently discarded; a newer local head is preserved when every incoming revision is already present. Preserve composition union semantics. Validate the final union, not each archive in isolation: a validated workflow referencing a pinned capability revision missing from a retained local history rejects the entire restore with `WorkflowDependencyMissing`. Drafts may remain unresolved. When the restore adds records, derive schema as max supported current/incoming version. For a no-additions restore, preserve the current schema exactly. A schema-4 workspace never downgrades even when all workflows are deleted. Preview and commit must derive identical plans against the same full state. Preflight restore against a noncreating read (or canonical empty state) before opening a creating connection. If the destination is absent and the recomputed plan adds nothing, verify the retained plan against that observation and return empty data without creating a directory/file, changing PRAGMAs or starting a transaction. This read observation is the no-op linearization point; a later independent writer is not claimed absent forever. If additions exist, only then permit creation, and revalidate full state and exact plan inside the immediate transaction before migration/data writes. Existing-workspace no-op restores validate the plan under the transaction but make no row, schema or metadata write. A no-additions restore does not migrate or write. A stale expected state rejects before mutation; restore has no stale-state bypass.

Every surviving workflow history reference with a syntactically valid capability ID to an existing owner blocks deleting that capability, even with malformed/missing revision ID in a draft. Existing composition/source dependencies still apply. Workflow deletion removes its owner and complete history only, not inputs or unrelated workflows. Source deletion remains blocked by dependent capability owners/composition histories; workflows reference capabilities, not sources directly. Inspect dependency lists before prospective deletion validation so the user can understand a blocked operation. Logical deletion does not claim secure erasure. Deletion remains exact-state guarded, never cascades, and never lowers schema version.

## Version routing and existing feature preservation

Before allowing schema 4 in `verify_schema`, audit every public store method and version comparison. Existing legacy source `save`, legacy capability APIs and legacy workspace data/backup/restore/deletion APIs reject schema 4 as they reject unsupported composition state. Existing `composition_data`, composition backup/export/restore and composition deletion DTO APIs also reject schema 4, including restores that would project away current workflow records. Native v1 data controls must surface that refusal until W2c adopts the complete v2 DTOs; no native command can create schema 4 in W2b.

The version-aware source `save_v1`, capability `*_v1` methods, composition preview/apply, source list/open and stored compilation remain functional on schema 4 while preserving complete workflows. Every mutation uses full workflow-aware record validation and complete state IDs inside the transaction; a source/capability/composition change cannot bypass workflow integrity. Schema-3-only table/byte-limit branches become explicit schema-3-or-4 branches where appropriate, not loose fallthrough. Legacy `workspace_data::read_image` must reject all unsupported richer versions. Capability revision append does not retarget workflow pins. A workflow validated against an older capability revision remains valid when the capability head advances.

Unknown schemas stay rejected before persistent PRAGMA changes. Existing V1/V2/V3 schema, state-ID and archive golden tests remain valid. Version-aware new backup/restore paths must use full records throughout; factoring shared helpers must not re-enable old projections. Native/renderer DTO adoption and full interactive operation are W2c/W3 work with their own tests.

## Errors, ownership and qualification

Add closed StoreError variants: `WorkflowInvalid` (`workflow_invalid`), `WorkflowNotFound` (`workflow_not_found`), `WorkflowConflict` (`workflow_conflict`), `WorkflowFull` (`workflow_full`), `WorkflowDependencyMissing` (`workflow_dependency_missing`). Invalid candidate/bad parentless-vs-new shape maps to WorkflowInvalid; nonexistent selected owner/revision to WorkflowNotFound; existing owner/head mismatch to WorkflowConflict; workflow count/history quota to WorkflowFull; missing validated pins on save/final-union restore to WorkflowDependencyMissing. Malformed IDs supplied to new W2b APIs use WorkflowInvalid; keep legacy source InvalidId and its snapshot-specific public code/message unchanged; malformed stored rows/history use Corrupt; malformed archives use BackupInvalid; global database allocation uses Full, including a valid bounded V3 payload that exceeds canonical SQLite allocation during decoding (legacy V1/V2 decode errors remain unchanged); stale state uses WorkspaceChanged; blocked deletion uses RecordInUse with wording including workflows. Errors never echo imported content, paths or SQLite diagnostics. Draft save does not fail solely because dependency observations are unresolved.
